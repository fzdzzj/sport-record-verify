# 判定引擎（add-verify-engine）开发总览

> 本文档用于**不读源码**也能完整掌握本次开发内容。配套文档：《判定引擎-接口手册.md》（全部接口 + 请求/响应示例）。

---

## 1. 做了什么（一句话）

在微服务骨架上实现了「运动记录真实性判定」完整闭环：**提交轨迹 → 分片落库 → 异步判定（规则链）→ 状态回调 → 申诉 → 管理员终判**，覆盖规范 `spec/changes/archive/add-verify-engine/specs/sport-record-verify/spec-delta.md` 的全部验收项，并在本地端到端运行验证通过。

## 3. 核心数据流

```
客户端 → POST /api/records（requestId + userId + 轨迹点数组）
  │
  ├─ ① 幂等检查：request_id 唯一键，重复 → 3004 返回原结果
  ├─ ② 事务内：插 sport_record（SUBMITTED）+ 轨迹点写入分片表 track_point_{userId%16}
  ├─ ③ 乐观锁 SUBMITTED→VERIFYING
  ├─ ④ 事务提交后发 RocketMQ 事件 SUBMITTED（MQ 不可用 → Feign 直调兜底触发判定）
  ▼
verify-service 收到事件（或直调）
  ├─ ⑤ 幂等去重（Redis SETNX，24h）
  ├─ ⑥ 拉取记录 + 轨迹 → 漂移预处理 → R1~R4 规则链 → 汇总判定
  ├─ ⑦ 写 verification_result（verdict/score/rule_hits 证据 JSON）
  ├─ ⑧ 发 VERIFIED / REJECTED 事件 + 回调 record 状态 PASSED(2)/REJECTED(3)
  ▼
REJECTED 可申诉：POST /api/records/{id}/appeal → 建申诉单 → 记录 REJECTED→APPEALING(4)
  ▼
管理员终判：POST /admin/api/appeals/{id}/review
  ├─ pass=true  → 记录 RE_PASSED(5)、申诉单 RE_PASSED(1)
  └─ pass=false → 记录 RE_CONFIRMED(6)、申诉单 RE_CONFIRMED(2)
```

## 4. 两个状态机（理解业务的关键）

**记录状态（record_db.sport_record.status）**

```
SUBMITTED(0) → VERIFYING(1) → PASSED(2)
                            ↘ REJECTED(3) → APPEALING(4) → RE_PASSED(5)
                                                       ↘ RE_CONFIRMED(6)
```
- 所有迁移都走乐观锁 `UPDATE ... WHERE id=? AND status=? AND version=?`，防并发错乱；
- 终态只有 PASSED / RE_PASSED / RE_CONFIRMED 三个，其余均可继续流转。

**申诉单状态（verify_db.appeal.status）**：PENDING(0) → RE_PASSED(1) / RE_CONFIRMED(2)，仅 PENDING 可被终判。

**判定结论（verify_db.verification_result.verdict）**：VERIFYING(0) / PASSED(1) / REJECTED(2)——与记录状态是两个独立体系。

## 5. 判定规则链（R1-R4，阈值全部可配置）

先做**漂移预处理**：单点瞬时速度 > 20 m/s 或时间间隔 < 0.1s 视为 GPS 漂移点剔除；漂移占比 > 30% 记 SOFT 证据。

| 规则 | 判定逻辑 | 级别 |
|---|---|---|
| R1 速度 | 10 点滑动窗口均值 > 5.5 m/s 且持续 ≥ 10 个窗口（≈连续 19 点） | **HARD** |
| R2 加速度 | 加速度突变 Δv/Δt > 3 m/s² 出现 ≥ 3 次 | SOFT |
| R3 停留 | 位移 < 5 m 的停留段累计 ≥ 5 分钟且占总时长 > 40% | **HARD** |
| R4 距离一致 | 累计轨迹距离 / 起终点直线距离 > 3.0 | SOFT |

**汇总规则**：出现 HARD → 拒绝；仅 SOFT → 默认拒绝（`verify.policy.soft-only-reject=true`，可配置为放行）；无命中 → 通过。**评分**：`min(100, 50 + 20×HARD数 + 10×SOFT数)`。

配置项（`verify-service`，Nacos 优先级高于本地 yml，改配置即生效，无需重启）：

```
verify.rules.v-drift=20.0            verify.rules.r1.speed=5.5
verify.rules.r1.window-points=10     verify.rules.r1.min-windows=10
verify.rules.r2.accel=3.0            verify.rules.r2.min-count=3
verify.rules.r3.min-minutes=5        verify.rules.r3.max-meters=5.0
verify.rules.r3.segment-ratio=0.4    verify.rules.r4.max-ratio=3.0
verify.policy.soft-only-reject=true
```

## 6. 关键设计决策（可直接讲）

1. **轨迹分片**：`track_point` 按 `user_id % 16` 拆成 16 张物理表（`track_point_0..15`），ShardingSphere 5.4.1 INLINE 分片路由。写轨迹必须携带冗余分片键 `user_id`。E2E 实测 100→表4、101→表5、102→表6、200→表8，其余分片 0 行。
2. **提交幂等**：`request_id` 唯一键兜底 + 乐观锁状态迁移，重复提交返回 3004 + 原结果（recordId + 当前状态）。
3. **跨库一致性**：记录在 record_db、判定在 verify_db，无强一致；以「记录状态机 + 乐观锁」为收敛点，事件重投/降级直调天然幂等。
4. **MQ 事件 + 降级**：`record-verify-events`（TAG: SUBMITTED/VERIFIED/REJECTED，DLQ：`record-verify-events-dlq`）。消费者用程序化 `DefaultMQPushConsumer`（rocketmq-spring 2.3.1 与离线 rocketmq-client 5.1.4 不兼容容器注解，见 §7）。本地无 MQ 时提交后自动走 Feign 直调触发判定（`POST /internal/records/{id}/verify`，幂等）。
5. **消费幂等/重试**：Redis `SETNX verify:event:{eventId}`（24h TTL）去重；失败按 `verify:retry:{eventId}` 计数，3 次后投 DLQ，避免无限重试。
6. **ShardingSphere 接入方式**（无官方 starter）：YAML API 代理数据源 `YamlShardingSphereDataSourceFactory`；`mode: Standalone + Memory` 仓库的官方 SPI 实现未随包发布 → 按 SPI 契约自实现 `MemoryStandalonePersistRepository` 并注册。
7. **snakeyaml 版本冲突**（技术栈固有矛盾）：ShardingSphere 5.4.1 依赖 snakeyaml 1.x（`Representer()` 无参构造），Spring Boot 3.2.4 需要 2.x（`TagInspector`）。解法：record-service 的 Spring 配置改用 `application.properties`（绕过 Spring YAML 解析），并把 snakeyaml 降级 1.33 给 ShardingSphere；其余模块不受影响。
8. **规则阈值可配置**：`@ConfigurationProperties(verify.*)`，引擎每次判定实时读取，无需 @RefreshScope 重绑。

## 8. 端到端验收结果（本地实测）

| 用例 | 结果 |
|---|---|
| 真实轨迹 3m/s×60 点 | 提交 code=0 → **PASSED**，score=50，无规则命中，driftRatio=0.0 |
| 同 requestId 重复提交 | **3004** + duplicated=true + 原 recordId |
| 伪造匀速 6m/s×120 点 | **REJECTED**，score=70，命中 R1_SPEED（HARD） |
| 申诉 → 终判维持拒绝 | 记录 → **RE_CONFIRMED(6)**；再申诉被正确拒绝（**3003**） |
| 新伪造 → 申诉 → 终判通过 | 记录 → **RE_PASSED(5)** |
| 轨迹分页 | total=60 / 每页 10 条 |
| 分片路由 | user%16 精确落片，非目标分片 0 行 |

单元测试：`verify-service/src/test/.../VerifyEngineTest.java` **10/10 通过**（含 R1-R4 各规则、漂移占比、阈值覆盖、证据 JSON 结构）。

## 9. 本地运行指南

```bash
# 1) 建库建表（MySQL root/1234）：依次执行 sql/01..04 脚本（04 为 16 张分片表）

# 2) 构建（离线本地仓库）
mvn -s .mvn-settings.xml clean install -DskipTests -o

# 3) 启动 verify-service（8083）
#    SPRING_APPLICATION_JSON 含数据库密码 + 静态服务发现（Nacos 关闭时）
$env:SPRING_APPLICATION_JSON='{"spring":{"datasource":{"password":"1234"},"cloud":{"nacos":{"discovery":{"enabled":false}},"discovery":{"client":{"simple":{"instances":{"record-service":[{"uri":"http://127.0.0.1:8082"}],"verify-service":[{"uri":"http://127.0.0.1:8083"}]}}}}}}}'
java -jar verify-service/target/sport-verify-verify-service-0.1.0-SNAPSHOT.jar

# 4) 启动 record-service（8082）
$env:MYSQL_PASSWORD='1234'
$env:SPRING_APPLICATION_JSON='{"spring":{"cloud":{"nacos":{"discovery":{"enabled":false}},"discovery":{"client":{"simple":{"instances":{"record-service":[{"uri":"http://127.0.0.1:8082"}],"verify-service":[{"uri":"http://127.0.0.1:8083"}]}}}}}}}'
java -jar record-service/target/sport-verify-record-service-0.1.0-SNAPSHOT.jar

# 5) 冒烟：提交一条真实轨迹 → 查判定结果（示例见《接口手册》）
```
