## 1. 两个 Redis 抢 6379 端口（重要）

**现象**：本机同时存在 Windows 原生 `redis-server` 和 Docker 容器 `sport-verify-redis`，两者都监听 6379。
服务实际连接的是**原生 Redis**（谁先绑定谁占端口），业务数据（榜单 ZSet、点赞计数、事件去重键）都写在原生 Redis 里。

**影响**：`docker exec sport-verify-redis redis-cli ...` 看到的是**空容器**，查不到任何业务数据，容易误判「数据丢失」。

**正确做法**：验证数据时用容器去连宿主机原生 Redis：
```bash
docker exec sport-verify-redis redis-cli -h host.docker.internal -p 6379 <命令>
```
不要直接 `docker exec sport-verify-redis redis-cli`（那看的是容器内空的 Redis 实例）。

**根治建议**（本地环境专用，不入代码）：二选一——
- 停止 Windows 原生 redis 服务，统一用 Docker 容器；
- 或让 Docker 容器改用宿主机其他端口（`6379:6379` 改为 `6380:6379`），服务侧配置同步改端口。

## 3. RE_CONFIRMED 的触发方式（终判维持拒绝）

公开接口规定「RE_PASSED 的记录不能再申诉」，所以无法直接在一条记录上连续走「申诉 → 改判通过 → 再终判驳回」来触发 RE_CONFIRMED。

**测试做法**：把申诉单状态重置为 PENDING 后，再走一遍「终判驳回」路径——触发的事件与生产完全同一条路径（发的都是 REJECTED 事件，回滚逻辑一致）。

> 这是验证口径问题，不改变生产状态机；生产上 RE_PASSED 即为终态，不会二次申诉。

leaderboard-service 拆分后，榜单查询路径从 `/record/api/leaderboard` 变为 `/leaderboard/api/leaderboard`。
