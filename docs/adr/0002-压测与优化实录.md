# ADR-0002：压测与优化实录（因果记录）

- 状态：**已接受**
- 日期：2026-09
- 关联变更：`spec/changes/archive/add-load-test-report/`
- 数据来源：`docs/perf/压测报告.md`（本 ADR 只记因果与取舍，完整数据见报告）

## 背景

功能闭环（骨架+校验引擎+好友+点赞+排行榜）完成后，缺「真实数据 + 坑与优化实录」——
交付标准（拦截率≥90%、真实通过率≥95%、P95<200ms）与 §12.3 A1 项（100/500/1000 并发 +
至少 1 个优化案例）需要实测落地。本 ADR 记录**每一步优化的因果**（优化前后快照），
供深入追问与后续调参引用；结论限定于本地单机环境（详见报告 §2 环境快照），不夸大。

## 决策与因果

### 1. 优化一：轨迹逐条 INSERT → 单分片批量 INSERT（开关 `record.track.batch-insert-enabled`）

- **现象**：基线三档并发（100/500/1000）吞吐恒定 ~36 QPS，与并发数无关——硬瓶颈 =
  HikariCP 10 连接 × 每请求 300 次逐条 INSERT（每请求占连接 ~270ms，10 连接上限 ≈37 QPS，
  与实测严丝合缝）；P95 随并发线性爆炸至 29.4s，错误率最高 12.35%。
- **动作**：`TrackPointMapper.insertBatch` 多值 INSERT（同记录分片键一致 → ShardingSphere
  单分片单语句）；连接池 `maximumPoolSize` 10→30（`MYSQL_POOL_SIZE` 注入）。
- **前后快照**：100 并发 QPS 35.5→136.8（3.9×）、P95 3,757→1,597ms；500 并发错误率
  6.85%→0%、P95 17,171→5,746ms。原始 CSV 留存 `docs/perf/data/raw/{base,opt}-c*`。
- **取舍**：基线逐条路径用配置开关保留——优化必须可回退、可复现对比；单批上限 500 防超长轨迹单语句过大。
  **现状（update-perf-optimized-defaults）**：优化路径（批量 INSERT）现为日常默认；复现逐条基线须显式
  `record.track.batch-insert-enabled=false`。历史前后快照数字不变，仍以上表实测为准。

### 2. 优化二：组合索引 `idx_record_seq(record_id, seq)` 消除轨迹查询 filesort

- **现象**：轨迹访问模式固定 `WHERE user_id=? AND record_id=? ORDER BY seq`，仅有
  `idx_record(record_id)` 时 EXPLAIN TREE 出现 `Sort: seq` 节点（filesort），300 行实际 3.71ms。
- **动作**：`sql/migrations/add-idx-record-seq.sql`（幂等：information_schema 守卫 +
  PREPARE/EXECUTE，MySQL 8.0 无 ADD INDEX IF NOT EXISTS）。
- **前后快照**：Sort 节点消失，1.85ms（~2×）；行数越大收益越大。Explain 前后采样留存
  `docs/perf/data/explain-{before,after}.txt`。
- **取舍**：迁移脚本**不进** `docker-entrypoint-initdb.d`——首次 initdb 直接带索引会让
  「无索引基线」无法复现（复现步骤见压测报告 §9）。索引选 `(record_id, seq)` 而非
  `(user_id, record_id, seq)`：record_id 近唯一已足够过滤，且未来若出现不带 user_id 的
  管理端查询仍可命中。

### 3. GC 观测：分配速率优化的因果证据 + 堆参数的权衡

- **因果（双赢）**：批量插入后 Young GC 次数 565→297（−47%，同为 ~15min 压测窗口）——
  逐条路径每请求构造 300 组 MyBatis 语句对象/参数器，批量仅 1 组，分配速率同因下降。
- **权衡（如实记录）**：试验性 `-Xms1g -Xmx1g` 固定堆使单次停顿均值 3.3→11.2ms，
  1000 并发突发下出现 3 次 55~147ms 的 G1 Evacuation 长停顿（年轻代一次性回收对象更多）。
  **结论：批量插入保留；固定大堆不采纳**，后续方向为 G1 自适应 + `MaxGCPauseMillis=50`。推荐启动可选 `-XX:MaxGCPauseMillis=50`（不停堆大小）；`-Xms1g/-Xmx1g` 仍不采纳。
  GC 日志留存 `docs/perf/data/raw/gc-record-{baseline,optimized}.log`。

### 4. 可用性设计：熔断降级「转人工」+ 双路补偿自愈（T11）

- **决策**：服务间依赖故障用 Resilience4j（Feign 熔断，10 次窗口失败率 ≥50% → OPEN 10s），
  入口流量用 Sentinel（网关路由级 QPS 5000）——**限流管流量、熔断管依赖**，职责分离，
  不强行统一到单一组件。
- **降级语义**：`VerifyApiFallback`（api 模块）统一抛 4001；提交链路捕获后走
  `VerifyDegradeService.degradeToManualReview`（乐观锁 VERIFYING→MANUAL_REVIEW(7)），
  主链路不挂；**MANUAL_REVIEW 是终态但不做黑洞**——verify 恢复后补偿任务探活成功即重放，
  verify 侧 `reconcileCallback` 以 verify_db 终判为权威对账收敛（实测 30/30 全部自动回到 PASSED）。
- **竞态修复**（本 ADR 的核心因果之一）：MQ 不可用→Feign 直调时，verify 实际慢于 Feign
  读超时完成判定 → 记录被误判转人工而 verdict 已 PASSED。收敛原则：**verify_db 的终判
  是唯一权威**，record 状态向它收敛（而不是相反）。
- **实测快照**：故障期 30/30 提交 200（P50 79.8ms）；熔断 OPEN 日志
  `CallNotPermittedException` 实证；恢复后 30/30 收敛。全流程见压测报告 §7.2。

### 5. 压测工具选型：自研单文件 JDK21 程序（不用 JMeter）

- **决策**：`scripts/perf/` 三个零依赖单文件程序（虚拟线程闭环模型 + 样本生成 + 验收集），
  `java scripts/perf/LoadTest.java` 直接运行。
- **理由**：① 本工程强调「每个组件都知道为什么」——自研 200 行能讲清闭环模型、
  Little 定律、百分位插值；② 样本构造必须严格对齐引擎阈值（五类伪造模式），JMeter 参数化
  反而绕远；③ 无需安装 JMeter/JDK8 兼容层。
- **取舍**：不追求分布式压测与协议丰富度——本项目口径是单机可复现实录，不是产品级压测平台。

## 首跑修复清单（环境问题，供排查同类问题引用）

全栈首次真实运行暴露并修复（详见压测报告 §8）：broker 未加载挂载配置（`mqbroker` 缺 `-c`）、
WSL2 cgroup v2 触发 JDK NPE 导致 PULL 全挂（`-XX:-UseContainerSupport`）、镜像缺 `ss` 致
healthcheck 永败（改 `/dev/tcp`）、宿主机 3306 冲突（`MYSQL_PORT` 参数化）、user-service 缺
`@MapperScan`、ShardingSphere 不解析数字占位（自实现 env 替换）、Feign 超时 vs 慢判定的
转人工竞态（终判对账收敛）。

## 后续项（不在本变更范围）

2. 吞吐天花板：演示 overlay `docker-compose.perf.yml` 可选 `innodb_flush_log_at_trx_commit=2`（默认 compose 仍为 1；崩溃最多约 1 秒已提交丢失；**生产禁止**）；提交侧批量聚合另案（提交侧发送已异步，不改消费线程参数，不声称新 QPS）；
3. Sentinel 规则切 Nacos 动态数据源；
4. 引擎阈值分运动类型（骑行误拦）与 R4 闭环路线合理性（真实环形跑误拦）。
