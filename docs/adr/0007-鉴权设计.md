# ADR-0007：鉴权设计——网关统一鉴权 + 双 token 轮换

日期：2026-09-12
状态：已采纳（add-jwt-auth 变更交付）

## 背景

- 项目此前**无任何认证鉴权**：6+ 处代码注释明确写着「骨架无认证鉴权，userId 由调用方显式携带，接 JWT 后改从 token 解析」。任何调用方可以伪造任意 userId，越权访问他人记录/点赞/好友/榜单——这是安全边界的硬缺口。
- 审批版 §4.1 已定：注册（BCrypt、手机号唯一、重复→2001）、登录（access+refresh token、错密码→401 并计失败）。错误码 1001（token 无效/过期）、1002（无权限/越权）已在 `ResultCode` 定义但从未被使用。
- 用户表 `user` 已有 `password_hash`/`phone` 唯一/`status` 字段（数据基础就绪，不改表）；内部探活已有手机号脱敏惯例。

## 决策

### 1. 为什么网关统一鉴权（而不在每个服务各自校验）

- **唯一入口 = 唯一信任边界**：外部流量只经网关进入（Nacos 内网服务名不可达外网），网关校验 token 后把身份以 `X-User-Id` 头注入下游，下游服务只信任这个头——「身份由网关认定」而非「调用方自报家门」。
- **越权防线收敛在一处**：若每个服务各自解析 token，密钥/库/策略会在 N 处漂移；网关统一校验后，下游服务与 Feign 内部调用都不再需要 token 知识。
- **内网信任边界**：网关注入 `X-User-Id` 时**覆盖**外部同名头，下游不信任客户端直接传的头（演示项目无存量前端，直接覆盖；生产如需旧客户端过渡，可在网关对下游改名）。
- 代价：网关是单点（已有 Sentinel 限流兜底入口流量）；token 校验是纯 CPU 的 HMAC 计算，毫秒级，不影响网关吞吐。

### 2. 为什么 refresh token 轮换（rotation）

- **防重放**：refresh 长时效（7d），若被截获且不轮换，攻击者可在 7 天内反复换新；轮换使每个 refresh **只能用一次**——刷新成功后旧 refresh 在 Redis 原子作废，重放旧 refresh → 401。
- **原子消费**：刷新用 Redis `GETDEL`（原子）消费旧 jti，并发刷新同一 refresh 只有一个赢家，天然解决「并发 refresh 导致旧 token 误作废」的竞态（替代方案「新旧短暂共存」有重放窗口，不采用）。
- **access 短时效**（15min）：业务接口每次请求携带，泄露窗口可控；过期后客户端凭 refresh 换新，无需重新登录。

### 3. 为什么 refresh 存 Redis（而非 DB）

- **TTL 天然对时效**：refresh 存活键 `auth:refresh:{userId}:{jti}` 的 TTL 与 refresh 时效（7d）一致，到点自动消失，无过期清理任务。
- **易作废**：轮换/登出/风控只需 DEL 对应 jti 键（DB 落 refresh_token 表还要扫表 + 建索引 + 迁移）。
- **可扩展**：后续账号锁定/登出所有会话可 `SCAN auth:refresh:{userId}:*` 批量作废。
- 代价：Redis 故障时 refresh 校验退化为「JWT 本身时效」（签名仍有效期内可换新）；演示项目接受，生产可加 DB 落法为可选项。

### 4. 为什么 HS256 + jjwt（而非手写 HMAC）

- HS256 对称签名：签发端（user-service）与校验端（gateway）共用一把密钥，无需非对称密钥分发。
- jjwt 0.12.x 是事实标准：签名/时效/claims 解析开箱即用，避免手写 HMAC 的时序攻击与边界坑（`type`/`jti` 声明、`sub` 解析都按规范实现）。
- 三段式依赖（api 编译 / impl+jackson 运行时）：编译期不绑定实现，可平滑升级。

### 5. 为什么 spring-security-crypto 而非 Spring Security 全家桶

- 只需要 BCrypt（密码哈希）；全家桶会引入自动安全过滤链，与「无状态、网关统一鉴权」的骨架冲突（默认 401 会拦截所有端点，需额外配置放行）。
- `BCryptPasswordEncoder` 独立可用，版本由 Boot BOM 管理，零额外配置。

### 6. 鉴权降级开关 auth.enabled（默认 false）

- 现状压测/演示脚本全部显式携带 userId；开关默认 false 让**代码先落地、行为不变**（降级为旧行为），验收 2-5 通过后再切 true，并同步更新压测脚本带 token。
- 开关在网关（强制校验 + 注入 X-User-Id）与下游服务（身份认定）**两端都读**：false 时网关透传、下游读显式值；true 时网关强制鉴权、下游以 X-User-Id 为准（显式值不一致 → 403 越权）。

### 7. 白名单

`/api/auth/**`（发 token 的端点）、`/internal/**`（服务间 Feign 契约）、`/actuator/**`（健康探针）、`/admin/**`（管理端暂不接鉴权，保持现状，后续变更接管理员鉴权）放行；其余路径一律要求 Bearer token。

## 备选否决

- **每个服务各自校验 token**：密钥/策略多点漂移，越权防线不收敛，网关形同虚设。
- **仅 access token 无 refresh**：15min 过期即需重登，体验差；长时效 access 又放大泄露窗口——双 token 是标准解。
- **refresh 不轮换**：7 天重放窗口不可接受。
- **refresh 存 DB**：需要建表/索引/迁移，作废与 TTL 都要扫表；Redis 的 TTL + 原子 DEL 更贴合。
- **手写 HMAC/JWT**：签名解析边界多，出错即安全洞；用标准库（jjwt）把复杂度交给社区验证。

## 后果

- 正面：越权从「调用方自报家门」升级为「网关统一认定身份」（越权 403/1002 是核心价值）；双 token + 轮换防重放；开关默认关闭，迁移成本可控。
- 代价：接入即需带 token（auth.enabled=true 后破坏性变更）；网关/服务各维护一份 ~20 行 token 解析（签发端 user-service 的 JwtUtil 与网关 JwtTokenParser 独立维护，密钥/声明两端对齐，注释互为印证）；Redis 是 refresh 校验的软依赖。
- 验收：`mvn clean install` 全量通过；注册→登录→拿 token→带 token 访问本人记录成功；无 token → 401；A 的 token 访问 B 的资源 → 403；refresh 刷新成功且旧 refresh 作废；auth.enabled=false 时旧行为可用。
