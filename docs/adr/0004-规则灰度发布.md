# ADR-0004：规则灰度发布（rule_version 快照 + userId%100 采样 + Redis 广播失效）

日期：2026-09-12
状态：已采纳（add-rule-grayscale 变更交付）

## 背景

- 「阈值可配」已落地（`VerifyProperties` + Nacos `verify.rules.*`），但一改全体用户立即生效：无版本化、无小流量采样、无回滚——新阈值有 bug 时全体用户直接承担误判。
- `rule_version` 表（version/rules_json/gray_ratio/status）骨架阶段已建但无任何代码使用；审批版 §7.4 设计了完整灰度流程（创建快照 → 采样观察 → 异常秒回滚 → 稳定全量），属规则灰度这一核心技术点的代码载体，也是「校验误判率超标 → 阈值可配 + 灰度调参」风险应对链的实锤。

## 决策

### 1. 采样路由：`floorMod(userId,100) < gray_ratio`，灰度分支读库内快照

- 灰度分支执行 `rule_version.rules_json` 快照而非 Nacos 实时值：快照落库后不可变，消除「灰度观察期配置又被改」的竞态，观察结果可信且可复现（规范「规则快照隔离」）。
- 采样键 `userId%100` 对同一用户恒定 → 同用户始终同分支，不随请求时序/实例抖动；`floorMod` 对负 userId 防御。
- 基线 = ACTIVE 版本快照（全量后「新版本变为基线」，同样不受 Nacos 瞬时变更影响）；尚无任何版本时回退 Nacos 实时配置——原「阈值可配」路径在无版本阶段完全不破坏。

### 2. 秒级回滚：路由行本地缓存（Caffeine ≤60s TTL）+ Redis pub/sub 广播

- 灰度/基线两把路由 key 缓存在各实例本地；管理操作后本实例立即失效，其余实例经 Redis 频道 `verify:rules:invalidate` 即时失效。Redis 不可用时发布仅告警、监听静默，全网退化为 TTL 收敛——回滚延迟上界 60s（规范「≤60s」），且广播不引入新故障面。
- 广播必须在 **DB 提交后**发出（activate 事务经 afterCommit 同步器挂载，与 record-service「事务提交后发事件」同一手法）：否则其他实例先收到广播、重查到旧状态回填缓存，反而把旧值续命一个 TTL。
- 版本快照 key（`verify:rules:v{version}`）不参与失效——快照不可变，只需按版本区分 key。

### 3. 状态机与并发：乐观迁移 + FOR UPDATE 串行化

- 状态迁移全部带 WHERE 前置条件（GRAY→ACTIVE 仅 `UPDATE...WHERE status=0`），影响 0 行即并发冲突。
- activate 事务内先 `SELECT...FOR UPDATE` 锁全部未退役行串行化并发发布，再 `retireOthers`（旧 ACTIVE + 遗留 GRAY 一并退役）后乐观晋升——双保险保证「同一时刻至多一个 ACTIVE」。
- 「至多一个采样中版本」服务层约束（countOtherSampling）：避免两个灰度版本争抢同一段 userId%100 采样桶。

### 4. 快照编解码：独立 ObjectMapper、忽略未知字段

- 快照格式要求跨时间稳定：`RulesSnapshotCodec` 绑定独立 ObjectMapper，与业务全局 bean 隔离，不随全局 Jackson 配置漂移。
- 反序列化 `FAIL_ON_UNKNOWN_PROPERTIES=false`：旧代码可读新版本写入的快照（多出新阈值字段不报错），保证灰度可回滚到旧版本。

### 5. 阈值类型维度（add-sport-type-threshold，规范「阈值按类型分维度」）

- **结构**：`VerifyProperties.Rules` 从「全类型共用一套 r1-r4」升级为 `Map<String, RuleThreshold>`（`by-sport-type`，key=SportType.name），每类型独立 R1-R4；R5 与运动类型弱相关，维持通用（空间真实性不随类型缩放）。
- **取值**：判定时引擎按记录 sportType 调 `threshold(SportType)`——命中类型配置用类型阈值，否则回退单套（RUNNING=5.5，历史默认）。标定：RUNNING 沿用 5.5、CYCLING 上限 15（正常骑行 6~8 m/s）、WALKING 3.5，来源为真实运动数据分位数。
- **兼容**：旧扁平结构（`rules.r1.*` 等）保留为回退载体，rules_json 缺类型维度时自动回退单套阈值——灰度既有版本不越界、可回滚。
- **正交性**：灰度路由（userId%100 选版本）与类型维度不耦合——先取版本快照，版本内再按 sportType 取阈值；两维度互不改变对方逻辑。
- **未知类型**：提交接口枚举白名单（RUNNING/CYCLING/WALKING）外取值拒绝（3007）；判定侧防御性回退 RUNNING。

### 备选否决

- **Nacos 配置灰度（beta 发布/多数据源）**：只能灰「配置集」不能灰「版本快照」，且与动态刷新竞态——正是本变更要消除的问题。
- **重启发布 / 全量开关**：无小流量验证与秒级回滚能力。
- **Redisson 分布式锁串行化发布**：管理端低频操作，FOR UPDATE 已足够，不引入额外协调成本。
- **Feature-flag 平台（Togglz 等）**：超配，且不解决规则快照版本化问题。

## 后果

- 正面：审批版 §7.4 全流程实锤。真实冒烟 4 场景全过（同一 5.8 m/s 轨迹：灰度 10% 时命中用户 PASSED / 基线用户 REJECTED；置 0 秒回滚后立即翻转；全量后全员走新规则），Redis 广播发送/接收均有日志与订阅端实证。
- 代价：校验入口新增路由读取——路由行与快照均命中 Caffeine（内存读，TTL 1min），对 P95 无感；`rule_version` 成为判定关键路径数据，需随 verify_db 备份。
- 已知边界：管理接口 Swagger 级无鉴权（骨架无 JWT，生产须加管理员鉴权）；分版本误判率对比监控（gray/active 打点）属后续可观测项；spec-delta 待 openspec archive 合入基线。
