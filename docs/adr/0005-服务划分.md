# ADR-0005：服务划分 4→5——榜单独立为 leaderboard-service

日期：2026-09-12
状态：已采纳（add-leaderboard-service 变更交付）

## 背景

- 审批版 §2.2 服务划分原为 4 服务（gateway/user/record/verify），榜单作为 record-service 的一个域内聚交付（LeaderboardService/Controller/EventConsumer/Contribution 全套 + `leaderboard_contribution` 表 + `leaderboard:overall` ZSet）；执行计划 P2「第 5 个榜单服务」列为可选深化项。
- 榜单与记录主链路的耦合面天然极小：读路径（ZSet 秒级）不碰记录表；写路径由 VERIFIED/REJECTED 事件驱动（与校验主链路解耦，最终一致）；唯一「反向依赖」是对 `sport_record` 的状态/里程读取与对 user-service 的好友/昵称 Feign 调用。
- 榜单读多写少（总榜/好友榜读流量随用户增长，入榜/回滚写流量随判定线性），与「记录分片存储 + 点赞」混布时互相挤占连接池/CPU，且故障面连通——榜单抖动会拖累记录主链路。

## 决策

### 1. 拆分方式：代码平移 + 复用 record_db（进程拆分优先于数据拆分）

- 榜单 6 个类整体迁至 `com.sportverify.leaderboard`（新服务 8084，Nacos 独立注册），逻辑逐行原样平移、行为等价（T8 冒烟前后一致），不借拆分重写。
- `leaderboard_contribution` 表**留在 record_db**（默认方案）：两服务共库、各管各表（record 写 sport_record/record_like/track_point，leaderboard 写 leaderboard_contribution），物理隔离拆 leaderboard_db 列为可选项——先跑通进程边界，避免一次性引入库迁移成本（与 ADR-0001「单实例三库逻辑隔离」同一哲学）。

### 2. 依赖边界：对记录域只读，结构上杜绝双写

- 榜单对 `sport_record` 的依赖收窄为**只读快照**：`SportRecordMapper` 刻意不继承 MyBatis-Plus BaseMapper、不提供写方法，仅一条 `@Select` 返回 4 字段投影（id/user_id/distance/status，入榜闸门所需的最小集）——写路径仍归 record-service，从接口层杜绝跨服务双写。
- `sport_record`/`leaderboard_contribution` 均为未分片单表，leaderboard-service 以普通数据源直查，**不引 ShardingSphere**（无 snakeyaml 1.x/2.x 冲突，配置回归 application.yml）。
- 事件消费切换为单消费者：`leaderboard-consumer-group` 随职责迁至 leaderboard-service 订阅 VERIFIED/REJECTED，record 侧原消费者与 `rocketmq.leaderboard.consumer.group` 配置同步下线——同一时刻仅一个服务沉淀榜单。
- Feign 契约随服务走：榜单查询契约从 RecordApi 迁出为独立的 `LeaderboardApi`（`@FeignClient(name="leaderboard-service")`），`LeaderboardDTO` 留在 api 模块跨服务共享。

### 3. 路由：独立 `/leaderboard/**` 前缀（破坏性变更，演示项目直接切换）

- 网关新增 `route-leaderboard-service`（/leaderboard/** → lb://leaderboard-service，StripPrefix=1）；`/record/api/leaderboard` 随 record 侧控制器删除自然失效。兼容期 302/双路由过渡在演示项目中选择省略（无存量前端契约），生产化场景应保留过渡期。
- 监控同步：prometheus.yml 启用预留的 8084 抓取 job，ServiceInstanceDown 告警 job 正则扩为五服务。

## 备选否决

- **拆独立 leaderboard_db**：贡献表单表单库，物理隔离收益低、迁移成本前置；列为可选后续项。
- **榜单留在 record-service、仅做读写分离**：不解决故障面连通与独立扩缩容，「为什么 5 个服务」无实体载体。
- **榜单并入 user-service（好友榜强相关）**：榜单数据源是判定事件与记录里程，与用户域无数据依赖，只会制造新的跨域耦合。

## 后果

- 正面：职责单一（record=记录读写+点赞，leaderboard=榜单读热+事件沉淀）；读热路径独立扩缩容；榜单故障面与记录主链路隔离；「为什么 5 个服务/榜单为什么独立」成为可讲的架构决策（数据热点隔离、读写分离、独立降级面）。
- 代价：多一个服务的部署/内存开销（演示机 5 JVM）；ZSet 热读层跨服务共享 Redis（键空间按职责划分，锁与去重键均 `leaderboard:*`/`lock:*` 前缀隔离）。
- 验收：`mvn clean install` 7 模块通过；T8 改判回滚全链路冒烟通过（REJECTED→申诉→RE_PASSED 加分 +7.14km，RE_CONFIRMED→REJECTED 事件自动回滚，锚点 ROLLED_BACK，结算任务清理幽灵分数）；经网关 `/leaderboard/api/leaderboard?type=overall/friend` 正常返回；Nacos 5 服务可见；record-service 不再暴露榜单接口（无 handler）；Prometheus 新 target UP。
- 已知边界：路由前缀 `/record/api/leaderboard → /leaderboard/**` 为破坏性变更（无兼容期过渡）；spec-delta 待 openspec archive 合入基线。
