# ADR-0003：监控选型（Prometheus + Grafana）

日期：2026-09-12
状态：已采纳（add-observability 变更交付）

## 背景

- 骨架阶段各服务只暴露 Actuator `health/info` 两个端点：无指标采集、无可视化面板、无告警，「监控告警」目前只能讲设计（执行计划 P2 扩展项）。
- 压测报告（ADR-0002）产出了 P95/吞吐/错误率等**一次性快照**，缺少持续观测载体验证优化效果的长期有效性。
- 本地环境内存预算 3-4GB，监控栈必须轻量，且能随 `docker compose up` 一键起停。

## 决策

### 1. 指标暴露：Micrometer + `/actuator/prometheus`（拉模式）

- Spring Boot 内置 Micrometer，服务侧只需加 `micrometer-registry-prometheus` 依赖 + 暴露端点，JVM（堆/GC/线程）、HTTP（QPS/P95/错误率）、HikariCP 连接池指标**代码零侵入**转成 Prometheus 文本格式。
- 选拉模式而非推模式：Prometheus 的 target 状态（`up` 指标）天然就是实例存活信号，「实例下线」告警零成本；抓取频率由服务端统一控制，坏实例不会反向打爆采集端。
- 版本口径：micrometer **1.12.4** 与 Boot 3.2.4 内置 micrometer-core 同源。注意本仓库父 pom 是自定义父（自行 import spring-boot-dependencies），同 POM 内无版本的 dependencyManagement 条目会**覆盖** BOM import 展开的条目（实测报 version missing），因此父 pom 显式锁 `${micrometer.version}=1.12.4`，升级 Boot 时同步。
- HTTP P95 依赖直方图 bucket：默认只有 count/sum/max（summary 型），必须开 `management.metrics.distribution.percentiles-histogram.http.server.requests=true`，否则 `histogram_quantile` 无数据。

### 2. 采集与告警：Prometheus（而非 InfluxDB / Zabbix / SkyWalking / 自研）

- Kubernetes 与云原生监控事实标准，文本格式指标 + PromQL + 告警规则生态成熟，单二进制 + TSDB，符合轻量要求。
- 四条告警规则（`prometheus/alert-rules.yml`）：实例下线（up==0 连续 1m，critical）、5xx 错误率>5%（连续 2m）、HTTP P95>200ms（连续 2m）、JVM 堆使用率>80%（连续 5m）。P95 阈值 0.2s 对齐审批版 §8.2 延迟预算（网关 10ms + 落库 50ms + 校验 100ms ≈ 160ms）；错误率 5% 对应 95% 可用性的错误预算惯例。
- 备选否决理由：InfluxDB 推模式、告警与生态弱于 PromQL；Zabbix 偏主机/网络监控，对 JVM/HTTP 指标建模别扭；SkyWalking 主打链路追踪（当前无 trace 需求，引入即超配）；自研成本不可控且无额外收益。

### 3. 可视化：Grafana（provisioning 全文件化预置）

- 数据源 + dashboard provider + 面板 JSON 全部落文件（`grafana/provisioning/`、`grafana/dashboards/`），compose up 即得 8 面板总览，演示**零手工配置**。
- 面板覆盖 spec-delta「可视化面板」要求：服务可用性、HTTP P95/错误率（带 200ms/5% 红线）、JVM 堆/GC、连接池，另含 QPS 与线程数。

### 4. 网络拓扑：监控栈进 compose，业务服务留宿主机

- prometheus/grafana join `sport-verify-net`；Prometheus 抓取 `host.docker.internal:8080-8083`（服务是宿主机 java -jar 进程），compose 侧配 `extra_hosts: host.docker.internal:host-gateway` 兜底 Linux 宿主机。
- 服务日后容器化，把 target 换成 compose 服务名即可（prometheus.yml 注释已留改法与 leaderboard:8084 空位）。

## 后果

- 正面：运维完整度补齐，压测数据有了持续观测载体；告警可现场演示 firing（停任一服务，1 分钟后 Alerts 页变 firing）。
- 代价：本地常驻多两个容器；Prometheus TSDB 限 7 天保留以控制资源。
- 安全口径：`/actuator/prometheus` 目前在服务主端口直连暴露，仅限本地演示；生产须内网抓取 + 网关不转发 actuator 路径（最小权限）。
- 已知边界：RocketMQ 消费位点等中间件内部指标需 broker 暴露或 exporter 支持，本提案先聚焦 JVM/HTTP/DB 指标；告警通知渠道（Alertmanager）属后续项，firing 目前只在 Prometheus 控制台可见。

## 补充（2026-09-16）：日志贯穿标识（MDC 最小实现）

指标面已齐，但一次「提交记录」跨 gateway/record/MQ/verify/MQ/leaderboard 的日志原先无法按同一 ID 对齐。
**不**引入 SkyWalking/Zipkin/Sleuth（与本 ADR「当前无完整 APM 需求、引入即超配」一致），改为：

- 网关 `X-Request-Id` 生成/透传/回写响应头；
- 各 MVC 服务 `TraceIdFilter` → MDC `traceId`；
- RocketMQ userProperty 透传同头；
- 统一 `logging.pattern.console` 输出 `[%X{traceId}]`。

**刻意不做**：把 UUID traceId 作为 Micrometer tag（高基数会打爆时序库）。日志与指标仍通过时间窗 + 实例标签关联。
