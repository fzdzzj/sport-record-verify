**判断 1：真正的债有三层，交接文档只看到了一层。**

## 4. 关键技术决策指导（给结论，不给选项）

### 决策 1：分支策略立刻改为「main 为唯一集成线，完成即合并」

现状是 4 条 feature 分支长期悬挂，最长落后 9 个提交。这是单人项目 + 面试展示场景里**最不该有**的结构风险。

**结论**：`main` 是唯一真相源；feature 分支生命周期 = 一次变更；**每次合并前先 rebase main**；合并后打 tag（`v0.5-rbac`、`v0.6-sport-type` 之类）。
**理由**：面试官看的是 main 的 README 和目录，不是分支列表；而「打开 main 就能 `docker compose up` 跑通」比「分支结构漂亮」重要 100 倍。
**纪律**：合并后 main 必须能编译 + 测试绿，**做不到就不要合**（这也是你 commit 规范里「保持可独立编译」的延伸）。

### 决策 2：二级缓存分支**不要直接 merge**，用 rebase + 逐 commit 走

它落后 main 9 个提交，与 sport-type 有 2 处交叉（`RuleVersionService`、`RuleCacheInvalidationListener`）。
**结论**：以 main 为基线 `rebase`，4 个 commit 粒度正好，一个 commit 一验。

**特别提示（我实际读了代码，这里给准确判断，别用错口径）**：
- 缓存 key 是 `verify:rules:v{version}`，值 = **整个 `VerifyProperties`**。sport-type 之后的类型阈值是 `VerifyProperties` 的**内部嵌套结构**，所以 key **不需要**带 sportType，**不存在「跨类型串味」问题**——这点可以放心。
- 真正的风险是**序列化往返**：`RuleCacheService` 用 Jackson `writeValueAsString` / `readValue(json, type)` 把 `VerifyProperties` 写进 Redis L2。而 `VerifyProperties.Rules` 在 sport-type 之后变成了「按类型分维度的嵌套阈值」。缓存分支的 fork 点**早于** sport-type（`git show feature/add-two-level-cache:.../VerifyEngine.java | grep -c sportType` → **0**），所以它的序列化代码**从未见过嵌套结构**。
- **最危险的是失败方式是静默的**：`readRedis` 里 `catch (Exception e) → log.warn + return null → 降级 DB`。也就是说，**即使 L2 往返全挂，服务照样正常跑，测试照样绿，只是 L2 永远不命中**。而「L2 不命中」没有任何断言会发现它——除非你专门断言。

**所以合并 B4 时必须做这三件事（写成 DoD，不是建议）**：
1. **加 L2 往返断言用例**：把带多类型嵌套阈值的 `VerifyProperties` 写入 Redis 再读出，断言「按 `CYCLING` 解析出的 R1 阈值 ≠ 按 `RUNNING` 解析出的 R1 阈值」——即证明嵌套结构真的活着，而不是退化成默认值。
2. **冒烟时直接看 Redis**：`docker exec sport-verify-redis redis-cli -h host.docker.internal -p 6379 KEYS 'verify:rules:*'`，再 `GET` 出来确认 JSON 里含 sportType 维度（记得坑 2：必须走 `host.docker.internal`）。
3. **压测复测 P95**：二级缓存是 README 压测数字的成因之一，实现变了不重测，README 的数字就变成了不实陈述。

### 决策 3：「二级缓存」口径必须归位（二选一，我推荐前者）

现状：`docs/微服务面试项目方案.md`、`docs/简历项目描述模板.md` 都写「Caffeine + Redis 二级缓存」，但 main 上 verify-service 只有 **Caffeine 本地缓存 + Redis pub/sub 失效广播**（`RuleVersionService` 用 `redissonClient.getTopic` 广播失效）。Redis 在这里是「失效通知」，不是「第二级缓存」。

**结论**：**走「合并分支让口径成立」这条路**，而不是改文档口径。
**理由**：「Caffeine + Redis 二级缓存」是简历关键词，而且缓存分支的「穿透/击穿/雪崩三防护」是实打实的加分弹药（空值哨兵防穿透、Redisson 锁防击穿、TTL 抖动防雪崩）。有代码支撑的弹药比改小文档口径划算得多。
**代价**：必须完成 B4（合并 + 复测），否则口径依然不成立。

### 决策 4：账号锁定用**新错误码**，不复用 1002

原提案在「1002 vs 新码」之间摇摆。**结论：新增 `1003 ACCOUNT_LOCKED`（HTTP 403 或 429）。**
**理由**：`1002 FORBIDDEN` 已被「数据隔离越权」占用。客户端需要区分「密码错（401）」与「被锁定（1003）」才能给出正确 UI 和重试节奏——**把「被锁」和「越权」混在一个码里，面试被追问「你的错误码怎么分层」时会减分**。代价只是错误码表 +1，值得。
**附**：文案必须明确（「账号已临时锁定，请 X 分钟后重试」），且**锁定态下不校验密码、不消耗 BCrypt**（这是防撞库的性能点，是这条变更最值得讲的地方）。

### 决策 5：ADR 编号与新增决策的边界

**结论**：
- `add-two-level-cache` 落 **ADR-0008「缓存分层与三防护」**（有真实技术选型：Caffeine vs Redis 分层、TTL 抖动参数、失效广播 vs 短 TTL 的取舍）。
- **不**为「分支策略」写 ADR。工程纪律属于 README/CONTRIBUTING，ADR 只记录**会被人挑战的技术选型**。
- 继续执行坑 3 的纪律：**ADR 编号以落盘文件序号为准**，任务书指定编号与落盘可能顺延。

### 决策 6：规范归档的「前置条件」和 tasks.json 口径

**归档前置条件（四条，全满足才归档）**：
1. 代码已在 **main** 上（不是分支）；
2. 编译绿 + 测试绿；
3. README 与 `docs/项目速览手册.md` 已同步（别再出现「main 的 README 把已做写成待办」）；
4. `spec-delta` 已合并进主规范。

**tasks.json 口径**：**回写真实状态**。理由：openspec 工作流的价值就在「实施清单可视化」，全部 `false` 等于自废武功；而且「我发现状态未回写并定了回写规范」本身就是可讲的流程洞察。

### 决策 7：GitHub 公开的仓库卫生（实测结论：低风险，但两步必做）

我扫了一遍，**总体健康**：`.git` 3.9M、最大跟踪文件 64K、`.gitignore` 覆盖 target/logs/中间件数据/路网与压测生成物。敏感面：
- `password: root`（多处）、`password: postgres`（mapmatch）；
- `gateway-service`/`user-service` 的 JWT `secret: ${JWT_SECRET:sport-verify-hs256-secret-key-...}`（**已有环境变量覆盖，带默认值**）。

**结论**：这两个都是「本地 demo 默认值」，**不是阻塞项**，但两步必做：
1. README 加一句口径：「配置文件中的数据库口令与 JWT 默认密钥仅用于本地 demo，生产请用环境变量注入」——**主动说明比被面试官问出来好**。
2. 首推前跑一次排查：`git ls-files | grep -iE '\.(env|pem|key|p12)$|secret'`，并确认 `scripts/mapmatch/data/`、`docs/perf/data/*.jsonl`、`target/` 都没进库。

## 6. 协作约定（承接交接文档 §7，新增两条纪律）

**沿用（不变）**：
- 选项式提问，一次 2-4 项，推荐项第一并标 `(Recommended)`（本文件末尾就按这个来）。
- 细粒度 commit：一个 step 一个 commit，conventional commits，body 中文「改了什么：为什么」，**commit 之间保持可独立编译**。用户要的是「拆得更小」，不是「message 更长」。
- 委派提示词四件套：只允许写哪些文件 + 最多修复 1 次 + 回报 ≤300 字 + 细节留文件里。
- 诚实原则不可破：不吹未实现；Canal/Seata「讲设计」；单人项目的「为什么微服务」= 负担控制。

**新增纪律 1：完成三件套（Definition of Done）**
一个变更算「完成」，必须同时满足：① 代码在 **main** 上；② 编译 + 测试绿；③ 规范与文档口径一致。
**只满足①的，叫「写完了」，不叫「完成」。** 这次接手最大的一课就是这个：4 个变更都「写完了」，但一个都没「完成」。

**新增纪律 2：证据纪律**
任何「已验证」的表述后面必须跟可复现命令 + 输出摘要。不接受「应该可以」「理论上没问题」。
反向也成立：**AI 的验证不能替代你的冒烟**，服务能不能起来、接口通不通，你亲自跑。
