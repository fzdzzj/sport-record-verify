# 运动健康助手 · 微服务面试项目方案（v2.0）

版本：v2.0 ｜ 依据：面试项目改造方案 v1.0 + 用户明确要求"微服务形态"

---

## 0. 核心决策（先读）

**范围仍是「运动记录真实性校验系统」闭环，但架构形态为微服务。**

- 诚实前提（也是你的面试话术）："我知道单人项目微服务是负担，所以我把服务数控制在 **4 个**，每个服务都有独立存储、独立演进理由，而不是为了微服务而微服务。如果团队资源受限，这个范围可以压成单体模块化——两者的代码边界是完全一致的。"
- 这条话术同时回答了面试官最可能的第一问："你为什么要上微服务？"
- **服务数量铁律：≤4 个。** 超过 5 个，单人写不完，面试官也会质疑真实性。

## 1. 服务拆分（4 个服务，每个都要能讲清"为什么独立"）

| 服务 | Bounded Context | 职责 | 独立存储 | 拆分理由 |
| --- | --- | --- | --- | --- |
| `gateway-service` | 统一入口 | 路由、JWT 鉴权、限流 | 无（无状态） | 入口与业务隔离；后续加安全策略不动业务 |
| `user-service` | 用户与账号 | 注册/登录、签发 JWT、用户查询、好友关系（申请/同意/列表） | user_db | 独立演进；其他服务只依赖它的 token 校验结果与好友列表接口 |
| `record-service` | 运动记录 | 轨迹提交/存储/查询、状态机持有者、记录点赞（仅 pass） | record_db（轨迹分片） | 数据量大（轨迹点分片），读写模式独立 |
| `verify-service` | 真实性校验 | 预处理 + 规则链判定、阈值配置 | verify_db | **核心差异化**；CPU 密集、规则变更最频繁，独立扩容/灰度 |

> 可选第 5 个（**建议不做，讲设计即可**）：`leaderboard-service` 榜单——只累计 PASSED + 改判回滚。面试讲"榜单为什么不单独拆"：读多写少、规模未到，先并入 record-service 查询层；量上来再拆（Redis + 快照表）。

## 服务 × 技术映射（调整后：每个服务既有业务深度又有技术亮点）

| 服务 | 业务深度（讲什么） | 落地的技术（实现） | 讲设计的技术 |
| --- | --- | --- | --- |
| gateway-service | 路由、JWT 鉴权、防刷 | **Sentinel 网关限流**（按路由/用户限流，对齐 5k QPS 目标） | 灰度路由（按 header/比例）、鉴权过滤器链 |
| user-service | 双向好友的并发互加与申请状态机 | **Redisson 分布式锁**（好友申请去重）、MyBatis-Plus 分布式 ID | 好友列表缓存（Redis + 失效） |
| record-service | 轨迹分片、审核状态机、点赞读热写冷、榜单改判回滚 | **ShardingSphere-JDBC**（轨迹点/点赞表分片）、Redis（点赞计数/ZSet）、Redisson（定时防重锁）、RocketMQ 事件、定时任务（快照结算 + 点赞异步落库） | XXL-Job（复杂调度）、ES（搜索） |
| verify-service | 规则链、误判/漏判权衡、规则灰度 | **Caffeine + Redis 二级缓存**（规则阈值）、**Nacos 规则灰度**（版本 + 用户比例 + 回滚）、**Sentinel 熔断降级**（校验被打爆时降级"转人工/快速失败"） | 线程池隔离、SkyWalking 链路追踪 |

**原则：每个中间件只落在有真实场景的服务上；加深度不加服务数（仍是 4 个）。** 新增技术均为高频面试题（分库分表、多级缓存、灰度发布、限流熔断、定时任务防重）。

**工程结构（Maven 多模块，对齐课程项目标准结构）**：父 pom 统一管理版本；`common`（统一 Result/错误码/全局异常/工具）；`api`（各服务 Feign 接口定义，接口与实现分离，如 record-api、verify-api、user-api）；4 个业务服务模块 + `gateway`；各服务独立库。跨服务调用一律走 api 模块的 Feign 接口——与 hmall 的 hm-api / daijia 的 service-client 同构，这是面试官熟悉的微服务标准工程结构，照此组织少踩坑、讲起来顺畅。

## 2. 服务间通信与分布式设计（面试深挖核心）

### 2.1 主链路与通信方式

```
App/测试客户端
   │ POST /records (JWT)
   ▼
gateway ──► user-service（校验 token 合法性，非必需可缓存）
   │
   ▼
record-service（保存记录，状态 SUBMITTED）
   │ 同步 HTTP（OpenFeign）调用
   ▼
verify-service（预处理 → 规则链 → 判定 pass/reject）
   │ 返回判定 + 规则证据明细
   ▼
record-service（状态迁移 SUBMITTED→VERIFYING→PASSED/REJECTED，落库判定证据）
   │ 入榜（仅 PASSED，贡献快照）
   ▼
（可选事件：改判时触发回滚）
```

- **为什么核心链路用同步 HTTP 而非 MQ**（面试必问，标准答案）：
  1. 链路短（2 跳），同步延迟可接受（P95 目标 <200ms）；
  2. 需要即时拿到判定结果完成状态迁移，异步会增加复杂度；
  3. 可重试 + 幂等兜底，不丢不重。
- **异步事件（已实现，RocketMQ）**：判定完成（VERIFIED/REJECTED）与改判回滚（REVERSED）由 record-service 发布事件，榜单刷新、审计日志、未来通知作为消费者订阅——主链路仍同步（要即时判定结果），非阻塞动作走事件，最终一致 + 消费幂等。面试讲"同步/异步边界"的完整答案。

### 2.2 幂等（微服务必考）

- 记录提交幂等：客户端生成 `request_id`（或按 record 业务键），record-service 唯一索引去重，重复提交返回原结果；
- verify 调用幂等：verify-service 按 record_id 缓存判定结果，重复调用不重复计算；
- 状态迁移幂等：乐观锁 `version`，非法迁移直接拒绝。

### 2.3 分布式事务：为什么这个系统**不需要**

- 诚实且加分的答案：**这条链路没有跨库强一致需求**。
  - 记录落库（record_db）与判定落库（verify_db）可以设计为"判定结果最终同步回 record-service"，中间态由状态机表达（VERIFYING）；
  - 入榜与判定之间允许短暂不一致，用**改判回滚补偿**收敛；
  - 结论：本地事务 + 状态机 + 幂等 + 补偿，优于引入 Seata 分布式事务（对 2 跳链路是过度设计）；
  - 事件与本地状态的一致性：消费侧幂等兜底（按 record_id 去重），如需强保证可讲"RocketMQ 事务消息（半消息 + 本地事务表）"，本项目普通消息 + 幂等消费即可。
- 面试追问"什么时候才需要分布式事务"：跨服务强一致、资金类场景——而我们的支付在二期，属于明确砍掉范围。

### 2.4 配置中心与动态阈值（微服务特色亮点）

- 规则阈值（速度上限、加速度阈值、停留判定参数）放 **Nacos 配置中心**，`@RefreshScope` 动态刷新，支持灰度发布——比"DB 参数表"更贴合微服务形态，且能讲"线上调参不用发版"。

### 2.5 注册发现 / 网关 / 调用

- Nacos 2.x（注册中心 + 配置中心）；Spring Cloud Gateway 路由 + JWT 鉴权；OpenFeign 服务间调用；可选 Micrometer Tracing 讲链路追踪设计。

## 3. 范围裁剪（继承 v1.0，微调）

### ✅ 保留（全部写出真实代码）
记录提交、轨迹预处理、规则链校验、审核状态机、申诉改判、榜单（仅 PASSED + 回滚）、阈值配置中心化、JWT 登录、Redis（token/榜单/热点缓存）+ Redisson（分布式锁）、RocketMQ（判定/回滚事件，异步解耦）、JUnit + 集成测试、造数据脚本、Docker Compose 一键起（Nacos + MySQL×3 + Redis + RocketMQ + 4 服务）。

### ❌ 砍掉 / 明确非本人实现
支付、赛事、奖牌、私信、帖子/评论/关注流 Feed、图片/文本机审模型、真实道路拓扑校准、地区榜、信用分。（好友关系与运动记录点赞保留，见下方小节）

### 好友与点赞（自洽增强，推荐做，约 +1 周）
- **为什么可以加**：它们挂在"校验闭环"上，不引入独立社区模块——好友榜=按好友关系过滤的 pass 里程排行；点赞=只允许对 pass 记录点赞。主线（真实性）仍是主角，社交只是配角。
- **好友（user-service 域，双向）**：两张表——`friend_request`（from_user、to_user、status：PENDING/ACCEPTED/REJECTED/CANCELLED）与 `friendship`（user_low、user_high，唯一索引，**存储时强制 user_low < user_high 规范化**）；接口：发起申请、同意/拒绝/取消、好友列表、待处理申请列表。拉黑讲设计不实现。面试点（都是弹药）：
  1. **并发互加**：A 申请 B、B 同时申请 A → 规范化存储 + 唯一索引 + 申请状态机去重，同一对用户只有一条关系行；
  2. **幂等**：重复申请不产生重复 PENDING；同意前校验申请存在且状态为 PENDING；
  3. **单写者**：ACCEPTED 后落一条 friendship，以申请单状态迁移为唯一入口，避免双写不一致；
  4. **为什么双向比单向复杂**：多一套申请/同意流程与 PENDING 状态，换来关系对等、双方知情；好友榜用好友列表过滤。
- **点赞（record-service 域）**：对 pass 运动记录点赞/取消；`record_like`（record_id、user_id 唯一索引=幂等防重复赞）；Redis 计数（INCR/DECR）+ 异步批量落库（攒批/定时），讲"读热写冷、最终一致"；**只允许赞 pass 记录**（与主线一致）。
- **好友榜（榜单子维度）**：Redis ZSet（member=user_id，score=pass 里程）；实现=按当前用户好友列表过滤 + ZRANGE；一致性沿用贡献快照 + 改判回滚。跨服务：user-service 提供好友列表接口，榜单查询 Feign 拉取。
- **代价（诚实）**：+2 张表、+若干接口、约 1 周工作量、+2-3 条追问面（点赞并发/幂等、好友榜缓存一致性、好友列表跨服务调用）；3.5 个月窗口内可控，2 个月档按第 3 节砍法处理。

### ⚠️ 降级为"讲设计"
四层审核漏斗、Seata 分布式事务、Canal 同步、榜单独立服务、链路追踪、ES 搜索。（RocketMQ 已实现，见第 2.1 节）

| 部署 | Docker Compose（Nacos + MySQL×3 + Redis + RocketMQ + 服务 ×N） | 一键起是演示关键；注意本地内存（约 3-4GB，RocketMQ 单 broker 精简配置） |

| 流量治理 | Sentinel | 网关限流 + verify 熔断降级/热点限流（防刷、防打爆） |

| 灰度发布 | Nacos 配置版本 + 用户比例放量 | verify 规则灰度，异常秒回滚（弹药 J） |
| 可观测 | Micrometer Tracing / SkyWalking | 链路追踪设计，不实现 |
| 不做 | Seata、K8s、ES | 没到量；讲设计不实现 |

## 5. 数据模型（每库精简表）

- **user_db**：`user`（id、phone、password_hash、status）；`friend_request`（id、from_user、to_user、status：PENDING/ACCEPTED/REJECTED/CANCELLED、created_at，索引(to_user, status)）；`friendship`（user_low、user_high、created_at，唯一索引(user_low, user_high)，存储时强制 user_low < user_high）
- **record_db**：`sport_record`（id、user_id、sport_type、start/end_time、distance、duration、status、version）；`track_point`（record_id、seq、lat、lng、timestamp、speed，分片：按 user_id % 16 或按月）；`leaderboard_contribution`（record_id、user_id、distance、status，改判回滚用）；`record_like`（record_id、user_id、created_at，唯一索引(record_id, user_id)）
- **verify_db**：`verification_result`（record_id、verdict、rule_hits JSON、checked_at）；`appeal`（record_id、reason、status、operator、recheck_result）
- **Nacos 配置**：`verify.rules.*`（各规则阈值）

## 6. 深挖弹药（面试讲故事的素材）

- **弹药 A（主，不变）**：校验引擎的误判 vs 漏判权衡——可配阈值 + 真实/伪造测试集自证（拦截率、误判率、P95）。
- **弹药 B（微服务新增）**：**"这个场景为什么不需要分布式事务"**——状态机 + 幂等 + 补偿 vs Seata，讲权衡。
- **弹药 C（副）**：榜单改判回滚的写放大/读放大权衡（贡献快照表）。
- **弹药 D（微服务）**：同步 vs 异步的判断标准——"链短同步、非阻塞异步、什么时候才上 MQ"；本项目：主链路同步（即时结果）+ 判定/回滚事件走 RocketMQ（解耦削峰、最终一致）。
- **弹药 E（技术取舍）**：**"这个项目为什么没用 Canal"**——Canal 的价值在"MySQL→异构存储（ES/数仓/其他库）免侵入实时同步"；本项目缓存一致性用"主动失效 + TTL"足够、无 ES/数仓，硬上属于为用而用；若未来上搜索/报表，Canal 才是候选。能讲"什么时候才该用"，比用了更能体现判断力。
- **弹药 F（并发社交）**：点赞的"读热写冷"设计——Redis 计数 + 异步批量落库 + 唯一索引幂等；好友榜 ZSet 按好友列表过滤；只赞 pass 记录保证与主线一致。
- **弹药 G（数据建模）**：双向好友的"并发互加/重复行"——规范化存储（user_low < user_high）+ 唯一索引 + 申请状态机单写者；对比单向关注为何更复杂、换来什么。
- **弹药 H（分库分表）**：ShardingSphere-JDBC 分片——分片键选 user_id（业务按"单用户记录"访问，天然路由到单分片）；跨分片查询的代价与规避（按记录 ID 路由、避免跨分片 join/聚合下推）；与 MyBatis-Plus 组合的坑。
- **弹药 I（多级缓存）**：Caffeine 本地 + Redis 二级——verify 高频读规则阈值，本地缓存省网络；一致性=主动失效（Nacos 变更广播）+ TTL 兜底；缓存穿透/击穿/雪崩防护（空值缓存、互斥重建、随机过期）。
- **弹药 J（灰度发布）**：Nacos 规则版本灰度——新规则按用户比例放量，异常秒回滚；灰度与全量规则对比（误判率监控），稳定后全量。
- **弹药 K（定时任务防重）**：@Scheduled + Redisson 分布式锁（榜单快照结算、点赞异步落库）——多实例不重复执行；什么时候才需要 XXL-Job（任务多、需调度编排/失败重试管理/分片广播）。

## 7. 里程碑（3-4 周，单人）

## 8. 面试讲法

### 30 秒版本
「我做了一个运动记录真实性校验系统，4 个微服务（网关、用户、记录、校验），Spring Cloud Alibaba + Nacos。用户提交 GPS 轨迹，校验服务通过漂移过滤和可配置规则链判定真实性，状态机管理审核与申诉，榜单只累计通过记录并支持改判回滚。我重点解决了三个问题：防作弊的误判/漏判权衡、跨服务链路不用分布式事务的一致性设计、规则阈值的动态灰度。」

### 追问应对表（微服务相关，新增）

| 追问 | 怎么答 |
| --- | --- |
| 为什么 4 个服务？ | 每个都有独立存储与独立演进理由；再多就是为微服务而微服务（点名校验服务独立扩容/灰度） |
| 主链路为什么不用 MQ？ | 链路 2 跳、要即时判定结果，同步延迟可接受；MQ 用在非阻塞事件（判定完成/回滚/审计）——一套自洽的同步/异步边界 |
| 跨库一致怎么办？ | 不需要强一致：状态机表达中间态 + 幂等 + 改判补偿；讲清什么时候才需要 Seata |
| 事件丢了/重复消费怎么办？ | 消费幂等（record_id 去重）+ RocketMQ 重试/死信；强一致场景可讲事务消息 |
| 为什么没用 Canal？ | 无异构存储强一致需求；缓存主动失效+TTL 足够；上 ES/数仓时才是候选（讲判断标准） |
| 点赞并发怎么处理？ | Redis 计数 + 异步批量落库；唯一索引防重复；最终一致可接受 |
| 好友榜怎么实现的？ | Redis ZSet（pass 里程）+ 按好友列表过滤；一致性沿用贡献快照与回滚 |
| 双向好友怎么避免重复/并发互加？ | 规范化存储（user_low < user_high）+ 唯一索引 + 申请状态机单写者；重复申请幂等 |
| 轨迹分片怎么做的？ | ShardingSphere-JDBC，分片键 user_id；按记录查询路由到单分片，避免跨分片 join |
| 校验规则缓存怎么保证一致？ | Caffeine 本地 + Redis 二级 + Nacos 变更主动失效 + TTL 兜底；讲穿透/击穿/雪崩防护 |
| 规则灰度怎么做的？ | Nacos 配置版本 + 用户比例放量，异常秒回滚；灰度/全量误判率对比 |
| 定时任务会重复执行吗？ | @Scheduled + Redisson 分布式锁防重；任务复杂化才上 XXL-Job |
| 怎么保证不丢请求/不重复处理？ | 幂等键 + 唯一索引 + 乐观锁 |
| Nacos 挂了怎么办？ | 本地缓存 + 重试 + 兜底直连配置（服务启动时拉取快照）——讲设计即可 |
| 单体不是更简单吗？ | 承认：单人确实单体更省；微服务是我要展示的技术实践，所以我控制了规模并讲清边界（这就是答案本身） |

（其余追问沿用 v1.0：误判怎么办、算法是不是自创、怎么证明有效、为什么自研规则链、并发下榜单一致性、为什么不上 MQ。）

### 诚实边界（必须守住）
- 只说你实现的：4 服务闭环、状态机、回滚、幂等、测试、Compose 部署。
- 说"设计过"的：Seata、Canal、链路追踪、榜单独立服务、四层漏斗、支付。
- 绝对不说的：15 微服务已实现、支付已接入、真实地图拓扑已上线。
