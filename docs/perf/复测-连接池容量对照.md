# 复测：提交链路连接池容量单因素对照（TASK-141，A-B-B-A 四轮 100 并发 × 2000 请求）

> 对应变更：`spec/changes/measure-submit-pool-capacity/`。本任务只检验一个因素
> `MYSQL_POOL_SIZE`（10 vs 20），附带完成提案要求的安全前置：`TimingHikariDataSource`
> 关闭与首次懒建池的并发交错修复。不预设 20 必然改善；不修改生产默认池容量、SQL、
> 索引、事务、JVM、MQ。开工基线 `8380e11d0ffde4342b1fdc9ff828adbbe191d197`（main，与
> 任务书一致）。四轮使用同一个 jar（SHA-256
> `197978fcbe52ebfad36aba9f76972bdb7ef169f5840cc29afedd55a292f1f7be`）。

## 结论：不推荐（本机、本负载、诊断开启条件下）

**候选值 20 未获得可复现的收益，且有一致的单事务变慢与 DB 并发上升的代价信号。**

1. **方向不一致**：两轮 B（池 20）的 QPS 110.63 与 163.70 分别差于和优于两轮 A（池 10，
   128.71 / 129.48）；P50 与 connWait 同样跨在 A 臂两侧。「两次候选轮次方向一致且相对
   基线可区分」不成立，不构成「值得进一步验证」。
2. **一致的代价信号**：两轮 B 的事务内 DB 段 P50 全部变慢——commit 30.3/29.8ms →
   61.3/46.2ms，trackWrite 20.5/21.3ms → 35.7/31.2ms，insertMain 2.65/2.66ms →
   4.11/3.81ms；MySQL `Threads_running` 峰值 28/18 对 A 臂的 14/13。机制方向：池加大把
   更多并发事务压进 MySQL，单事务执行普遍变慢，收益却不稳定。
3. **稳定性反转**：A 臂同条件复现紧密（QPS 差 0.6%、connWait P50 差 3%、各分段几乎
   逐项一致）；B 臂仅池大小一项相同下 QPS 跨 48%（110.6→163.7）。候选值 20 在该环境下
   行为不可稳定复现。
4. **非错误性判定**：四轮全部 2000/0/0（0 限流 0 错误）、GC 与堆内存在各池容量下无一致
   差异（GC 暂停 147~167 次、总 637~665ms）。「不推荐」的依据是「无一致收益 + 一致的
   单事务变慢/DB 并发上升」，不是错误率或资源故障。

按提案停止条件就此收口，不追加轮次凑结果；候选 20 若要翻案，需要能解释 B 臂轮间
48% 波动来源的新证据，而不是在同一条件下再跑两次。

## 安全前置：关闭与首次建池并发交错（红 → 最小修复 → 绿）

**静态交错窗口（修复前）**：`getConnection()` 先读 `closed`（入口检查），之后才在
`innerPool()` 的 `synchronized(this)` 内懒建池；`close()` 不经该锁直接读 `pool`。首次取
连接通过入口检查后、建池前，另一线程可完成 `close()`（读到空池返回），随后首次取连接
仍建出无人关闭的内层池；优雅关闭后等于重开一个泄漏的连接池。

**判别构造（不依赖睡眠碰运气）**：主线程先占住包装类建池管程（`innerPool` 的
`synchronized(this)`）→ 首次取连接线程阻塞在管程入口（`Thread.State.BLOCKED` 静态证明
其已通过入口检查且当时 `closed=false`）→ 主线程在其等待期间完成 `close()` → 放行首次
取连接。等待一律以条件为准（线程状态轮询 + 截止时间），不用固定时长制造交错。

**行为红（修复前，未修复实现实跑）**：两条交错判别（无参重载与
`getConnection(username, password)` 重载）同语句失败——
`close 完成后包装类不得再创建内层池（该池由本包装类新建且无人关闭） ==> expected: <null>
but was: <HikariDataSource (HikariPool-4)>`（凭据重载轮为 HikariPool-5）；同轮其余 8 条
用例（含「内层池已建立 + 另一线程池内等待连接时 close 及时完成且重复 close 幂等」守卫）
通过。命令 `mvn -o -s .mvn-settings.xml -pl record-service -am clean test
-Dtest=TimingHikariDataSourceWiringTest -Dsurefire.failIfNoSpecifiedTests=false` rc=1
（10 run / 2 failures / 0 errors）。

过程注记：首次红跑将 `connectionTimeout` 设为 200ms，低于 HikariConfig.validate 的
250ms 下限，`buildPool` 先抛 `IllegalArgumentException` 掩盖了目标行为红（33ms 即失败）；
修正为 250ms（HikariCP 允许的最小值，与本文件既有用例同值）后重跑取得上述行为红。
该过程未当作证据，红仅以最终一次为准。

**最小修复**：`innerPool()` 建池临界区内复查 `closed`，已关闭即在锁内拒绝（不建池）；
`close()` 先置 `closed`，再在同一 `synchronized(this)` 内读取内层池引用，内层池关闭在
锁外执行。锁只覆盖懒建池构造与 close 的引用读取；稳态取连接走无锁 fast path，内层池
`getConnection`（最长 30s 池内等待）不持包装类锁。两个 `getConnection` 重载共享同一
边界；重复 close 幂等（内层 Hikari close 幂等 + 关闭状态已标记）。

**绿（修复后）**：`TimingHikariDataSourceWiringTest` 10/10（86 → TASK-140 收口后 100 →
本任务 +3 只增不减）。正式门槛：`bash scripts/verify/mvn-verify.sh --mode=offline --pl
record-service test` **rc=0**（**103/0/0/0**）；同入口 `package` **rc=0** 并产出唯一
实验 jar（SHA-256 见文首）。修复通过后才启动压测。

  MySQL `max_connections=151`、容器起时 `Threads_connected=1`（池 20 下预计峰值 ~41，
  实测见下表）；开工积压 SUBMITTED/VERIFYING=0、outbox PENDING=0；中间件容器
  nacos v2.3.2 / mysql 8.0.46 / redis 7.2 / rocketmq 5.2.0 全部 healthy。
- **固定程序**：每轮重启 record JVM（`MYSQL_PORT=3307` +
  `--record.submit.tx-timing-enabled=true` + 唯一轮 GC 日志文件），仅轮换
  `MYSQL_POOL_SIZE`；health 200 + 网关路由探测通过后跑
  `bash scripts/perf/run-perf.sh load 100 2000 <label>`（内置 10 条预热）；负载期间每 2s
  采样 MySQL `Threads_connected/Threads_running`、`record_db` processlist 连接数与 record
  进程 CPU/内存；轮后留存末条 `SUBMIT_TX_TIMING` snapshot，再排空（SUBMITTED/VERIFYING=0
  且 outbox PENDING=0，5s 间隔轮询，四轮分别 23/23/23/24 次 ≈115~120s）并复查四服务健康，

## 判定对照（按提案/spec-delta 判据）

- 「两次候选轮次的方向一致且相对基线范围可区分、无额外错误或明显资源恶化」：**不成立**
  （两轮 B 方向相反且跨在 A 臂两侧）→ 不得称「此环境下候选值 20 值得进一步验证」。
- 「两臂区间重叠、运行条件漂移或 DB 饱和及错误增加」：成立（重叠 + 漂移；无错误）→
  判定为**不确定或不推荐**；本报告取**不推荐**，理由：除无一致收益外，两轮 B 在三个
  事务内 DB 段与 `Threads_running` 上呈现**同方向**的代价信号，且 B 臂同条件复现失败。
- 反例（阻止更强结论的证据）：pool20-r2 单轮在所有请求指标上全面优于两轮 A——该单轮
  优势在 pool20-r1（全面差于两轮 A）上被同池重复否定，不构成因果。

## 口径边界

- **connWait 不是纯池排队**：它从进入包装类 `getConnection` 计到返回物理连接，含
  HikariCP 池内等待与可能的建连开销，不区分二者。
- **四轮均为诊断开启态**（`tx-timing-enabled=true`）：本报告数字不得当作生产默认关闭
  状态的性能或收益。TASK-140 的 connWait P50 527.1ms 是**旧诊断轮**（运行条件与本次
  不同），不是本次同条件基线，二者不构成同条件对照。
- 未做独立 P50 相减；各段独立 P50 不可相加为单请求延迟或构成占比。
- 本变更未修改生产默认池容量（`sharding.yaml` 的 `${MYSQL_POOL_SIZE:10}` 未动），未改
  JVM、SQL、索引、事务边界、MQ；四轮后已停全部四个 Java 服务并核对无运行中的诊断进程，
  诊断仅以启动参数存在过。

## 未覆盖与混杂因素

- **pool10-r1 的进程 CPU/内存未采集**：采样命令的 PowerShell 字符串插值缺陷导致该轮
  proc 采样只记录了属性名。该轮请求/connWait/MySQL/GC 指标完整；A 臂 CPU/内存由
  pool10-r2 覆盖。未为补采样重跑负载（避免超四次预算）。
- **B 臂轮间 48% QPS 波动的来源不可分离**：DB 缓冲池新鲜度、后台 relay/校验活动、
  JIT 状态等候选因素未控制；A 臂未出现同量级波动，故不能归因为与池大小无关的一般噪声，
  只能如实登记为该候选在单因素重复下的不稳定。
- **单机单负载**：c100×2000、16 用户轮转、每请求 300 点模板；gateway/user/verify JVM
  四轮共用（JIT/缓存随轮次演进），对四轮同置但非全新态。
- **数据增长**：四轮各落库 2010 条（2000 + 10 预热），主表 32382 → 40422，
  track_point 总行数约 +241 万（≈742.6 万）；未清库，符合容量预算。
- 原始 raw/log（summary/json/csv、proc tsv、snapshot、env 指纹、GC 日志）在既有忽略
  目录 `docs/perf/data/raw/` 与 `logs/`，不入库。
