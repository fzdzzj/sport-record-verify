## 提示词 B4 —— 二级缓存 rebase + 合并 + L2 往返断言

```
【任务】把 feature/add-two-level-cache 集成到 main（rebase + 合并），并补一项 L2 序列化往返断言测试。

【只允许写哪些文件】
- 允许：verify-service/src/main/java/com/sportverify/verify/**（含新增 RuleCacheService / TwoLevelCacheProperties / RuleNacosConfigListener 等）
- 允许：verify-service/src/main/resources/application.yml
- 允许：verify-service/src/test/java/com/sportverify/verify/**
- 允许：新增 docs/adr/0008-二级缓存.md；更新 docs/项目速览手册.md、docs/微服务面试项目方案.md、README.md（仅限与缓存口径相关的段落）
- 允许：spec/changes/add-two-level-cache/**
- 禁止：改动 record-service 的任何配置（坑 1：record-service 永远不加 yml）
- 禁止：改动 user-service / gateway-service / leaderboard-service / mapmatch-service 的业务代码
- 禁止：触碰 docs/perf/** 里的历史压测数据（复测产生的新数据放 docs/perf/data/ 下新文件）
- 声明：无其他写入者。需越界时停下来上报。

【必读材料（先读再动手）】
1. spec/changes/add-two-level-cache/proposal.md、tasks.json
2. spec/changes/add-two-level-cache/specs/sport-record-verify/spec-delta.md（缓存分层能力域，注意数清需求与场景数）
3. docs/adr/0008-二级缓存.md（该分支已写好，rebase 后确认它没被覆盖）
4. docs/项目指导-后续任务与风险指导意见.md 的「决策 2」与「R2」——**这是本任务的核心风险描述**
5. 现有代码：verify-service/.../service/RuleVersionService.java、consumer/RuleCacheInvalidationListener.java

【关键现状（不要重复造轮子）】
- 该分支**已实现完整**，不要重写、不要「顺手优化」。你的工作是：rebase → 解决冲突 → 补一个断言测试 → 验证。
- 缓存 key 形如 `verify:rules:gray` / `verify:rules:v{version}`，**值 = 整个 VerifyProperties**。sport-type 之后类型阈值是 VerifyProperties 的**内部嵌套结构**，所以 key **不需要**带 sportType。
- ⚠️ **本任务唯一的高危点**：RuleCacheService 用 Jackson `writeValueAsString` / `readValue(json, type)` 把 VerifyProperties 写进 Redis L2；而 `readRedis` 的实现是 `catch (Exception e) → log.warn + return null → 回源 DB`。
  **也就是说：序列化/反序列化一旦对不上嵌套结构，L2 会「静默永不命中」——服务不报错、测试照样绿、压测数字失实。** 这不是理论风险：该分支 fork 点在 sport-type 之前，它的序列化路径从未见过嵌套阈值。
- 另外：`RuleVersionService` 在这两条分支上都被改过（sport-type 改了阈值解析，cache 分支改了缓存读写），这是冲突集中区。

【执行步骤】
1. 记录基线：git log --oneline -1 main；git status --short（应为干净）
2. rebase（不要直接 merge，要以 main 为基线、逐 commit 走，保住 4 个 commit 的粒度）：
     git checkout feature/add-two-level-cache
     git rebase main
   冲突集中在 RuleVersionService.java、RuleCacheInvalidationListener.java、docs/项目速览手册.md。
   取舍口径：**以 main 的 sport-type 语义为准，把该分支的缓存读写挂上去** —— 即「按 sportType 解析出的阈值结构」必须保留，缓存层只负责读写它，不得把结构改回扁平。
   **最多修复尝试 1 次**；仍不通过就 `git rebase --abort` 并如实上报，不要为了过而删功能。
3. 合并：
     git checkout main
     git merge --no-ff feature/add-two-level-cache
4. **写 L2 往返断言测试（本任务硬性交付，不可省）**
   新增或扩展 verify-service 的测试，断言「序列化 → 写 Redis → 读回 → 按类型取值」这条链路真的活着：
   - 构造一个含**多运动类型嵌套阈值**的 VerifyProperties（至少 RUNNING 与 CYCLING，且两者 R1 阈值必须不同）
   - 经 RuleCacheService 走一遍真实读写（可用嵌入式/本地 Redis，或对该分支已有的测试基建复用）
   - 断言：读回的对象里，**按 CYCLING 解析出的 R1 阈值 ≠ 按 RUNNING 解析出的 R1 阈值**，且等于写入前的值
   - 再补一个**负向断言**：故意让反序列化失败，断言此时不会「悄悄返回默认值」而被上层当成命中的正常值（证明静默降级是可观测的，至少进 warn 日志）
   测试方法上必须用中文 Javadoc 写清「为什么要有这个测试」。
5. 校验（全部要贴输出摘要）：
     mvn 编译 + 测试（用 JDK21 显式启动，见 docs/项目指导-后续任务与风险指导意见.md 第 7 节；Git Bash 直接 mvn 会报 classworlds 找不到主类）
     期望：BUILD SUCCESS，且用例数 >= B1 完成后的基线（不许出现用例减少）
     git branch --merged main | grep two-level-cache
     grep -c "sportType" verify-service/src/main/java/com/sportverify/verify/service/RuleCacheService.java   # 若为 0，说明它确实不依赖类型维度，属正常；
     grep -c "sportType" verify-service/src/main/java/com/sportverify/verify/algorithm/VerifyEngine.java     # 期望 >=1，证明 sport-type 没被 rebase 掉
6. 冒烟（**这步只给命令，不许声称已通过** —— 真机冒烟由用户亲自跑）：
     docker exec sport-verify-redis redis-cli -h host.docker.internal -p 6379 KEYS 'verify:rules:*'
     # 再 GET 出值，确认 JSON 里含 sportType 维度的键（坑 2：必须走 host.docker.internal，直接 redis-cli 看到的是空容器）
   **把「请在服务启动并触发一次校验后执行上述命令」写进回报**。

【验收项（DoD，缺一不可）】
1. feature/add-two-level-cache 出现在 git branch --merged main
2. 编译 BUILD SUCCESS + 测试 BUILD SUCCESS（用例数不低于基线，贴总数那行）
3. 新增的 L2 往返断言测试存在，且**断言了 CYCLING 与 RUNNING 的 R1 阈值不同**（贴测试方法名 + 断言那一行）
4. VerifyEngine 里 sportType 仍在（grep 计数 >=1），RuleVersionService 仍含缓存读写
5. docs/adr/0008-二级缓存.md 在 main 上存在，且 docs/adr/ 下 0007 与 0008 并存
6. 回报中明确声明「压测复测与真机冒烟未执行，交用户执行」

【commit 计划（保持可独立编译）】

- 新增测试单独一个 commit：test(cache): L2 序列化往返断言（证明嵌套阈值不丢）

- 合并提交由 git 自动生成

【明确不在本任务范围】
- 不跑压测、不改 docs/perf/压测报告.md 的历史数字（复测由用户跑，数字由用户确认后另行更新）
- 不动 record-service 配置、不做规范归档（规范归 B3）

【回报格式（≤300 字，不要贴代码）】
- 产出：commit hash 列表 / 新增测试文件路径与行数
- 校验：6 条验收项实测结果（编译与测试各贴关键 1-3 行；第 3 条贴断言原文）
- rebase 冲突取舍结论：哪几个文件、按什么口径取的（各一句）
```
