# 运动健康助手 · 面试项目改造方案

版本：v1.0 ｜ 依据：对原《项目任务提示词 v3.2》及三份文档的诚实评估

---

## 0. 核心决策（先读这一节）

原项目是「15 微服务 + 45 功能 + 6 个月团队排期」的产品级规划，**不能作为单人面试项目的实现范围**（详见改造前评估：支付需企业资质、机审/拓扑校准属算法团队、广度稀释深度、AI 生成设计稿≠已实现系统）。

**改造决策：把范围砍成一个闭环——「运动记录真实性校验系统」。**

- 一句话定位：**一个能判断"这条跑步记录是不是真的"的后端服务。**
- 为什么是它：
  1. 差异化最强——Keep 类项目烂大街，防作弊/真实性校验是少数有技术含量、能讲出设计深度的点；
  2. 边界清晰——输入是轨迹数据，输出是 pass/reject + 结构化原因，可演示、可量化；
  3. 可演示——同一套代码，真实轨迹判通过、伪造轨迹（匀速刷数据/原地抖动/飞点）判驳回；
  4. 可量化——拦截率、误判率、P95 响应时间，都是面试官爱听的数据。

### ❌ 砍掉 / 明确"不是我实现的"

支付、赛事、奖牌、私信、社区图文、好友/地区榜、App 端、图片/文本机审模型、道路拓扑校准（真实地图）、15 微服务、MQ、K8s。

- 面试话术（诚实版）：「整个产品我参与过方案设计，但我的实现聚焦在真实性校验这个闭环。支付、社区那些是团队/二期范围，我可以讲设计思路，但不会说是我写的。」

四层审核漏斗、信用分、榜单快照结算——**讲设计**，但只实现其中的最小切片（榜单回滚）。

## 2. 技术栈（面试必问"为什么这么选"）

| 选型 | 理由（面试话术） |
| --- | --- |
| Java 17 + Spring Boot 3 | 主流后端栈 |
| **单体模块化**（按 bounded context 分包），不做微服务 | 单人项目微服务是负担；模块化保留拆分可能——"如果校验引擎要独立扩容/灰度，会把它拆成独立服务，因为它是 CPU 密集且变更最频繁的" |
| MySQL | 主存储；轨迹点分片表（按 user_id 取模 或 按月） |
| Redis | 榜单缓存（可选，二期再上也能讲） |
| 自研规则链（简单策略模式） | 不引 Drools——"规则数量可控，自研更好讲、可测试、可配置化" |
| JUnit 5 + H2/Testcontainers | 集成测试 |
| Docker Compose（可选） | 一键起 MySQL + 应用，演示加分 |

**不要碰**：Spring Cloud 全家桶、K8s、消息队列——没有真实流量需求，讲了只会被追问到答不出。

## 3. 系统设计（每个深挖点都要能讲 5 分钟）

### 3.1 校验引擎（主深挖点）

- 流程：原始轨迹 → **预处理**（剔除漂移点：速度突变、位置回跳；按距离阈值聚类去抖）→ **规则链逐条判定**（每条规则输出：命中/未命中 + 证据 + 可配阈值）→ **汇总判定**（任一硬规则命中 → reject；软规则累计 → reject）。
- 规则示例：
  1. **速度阈值**：单点速度 > 人类极限（如 5.5 m/s 持续 N 点）→ 硬规则；
  2. **加速度突变**：相邻点速度差过大（如 >3 m/s²）→ 漂移特征；
  3. **停留检测**：长时段位移≈0（原地抖动刷时长）→ 可疑；
  4. **距离一致性**：GPS 累计距离 vs 直线位移比值异常（折返过多）→ 可疑。
- 关键设计点（面试讲这些）：
  - 阈值全部可配（DB 参数表 + 缓存），"上线后按误判率数据调参"；
  - 规则链可插拔（策略模式），新增规则不改主流程；
  - 预处理与判定分离，"先清洗再裁决"。
- **自证数据**：用两类测试数据对比——真实跑步轨迹（通过率 ~95%+）vs 伪造轨迹（匀速直线/原地抖动/手画折返），拦截率 >90%。

### 3.2 审核状态机（副深挖点）

- 状态：`SUBMITTED → VERIFYING → PASSED / REJECTED`；`REJECTED → APPEALING → RE_PASSED / RE_CONFIRMED`（申诉后仍驳回）。
- 设计点：
  - 状态流转只允许合法迁移（状态机表/枚举校验），防止非法跳转；
  - **幂等**：同一记录重复提交/重复回调不重复计算、不重复入榜；
  - **回滚**：榜单只累计 PASSED；记录被改判（pass→reject）时回滚其贡献——用"按记录 ID 的贡献快照/增量表"实现，讲清为什么不用直接删。
- 面试追问预备：并发下两个请求同时改状态怎么办？（乐观锁版本号）

### 3.3 数据模型（精简版）

- `sport_record`：id、user_id、sport_type、start/end_time、distance、duration、status、version（乐观锁）；
- `track_point`：record_id、seq、lat、lng、timestamp、speed（分片表：按 user_id % 16 或按月分区，理由：轨迹点量大、只追加、按记录查询）；
- `verification_result`：record_id、verdict、rule_hits(JSON：每条规则的证据明细)、checked_at；
- `appeal`：record_id、reason、status、operator、recheck_result；
- `threshold_config`：rule_key、value、description（阈值可配置落点）。

### 3.4 两个"深挖弹药"（面试讲故事的素材）

- **弹药 A（主）**：校验引擎的误判 vs 漏判权衡——阈值调高则漏放作弊、调低则误伤真实用户。你用什么方法定阈值？（用真实数据分布 + 测试集，讲"我会怎么调"而不必真做数据科学）
- **弹药 B（副）**：榜单一致性——为什么用"贡献快照表 + 改判回滚"而不是实时 sum？（写放大 vs 读放大权衡）

## 5. 面试讲法

### 30 秒版本
「我做的是一个运动记录真实性校验系统：用户提交 GPS 轨迹，系统通过漂移过滤和规则链判断记录是否真实，输出 pass/reject 和结构化原因，支持申诉改判，榜单只累计通过记录并支持回滚。核心难点是防作弊的误判与漏判权衡。」

### 5 分钟深讲（顺序）
背景（Keep 类产品、反作弊是信任基座）→ 我的范围（只做校验闭环，其余是团队/二期）→ 挑战（伪造数据花样多、误判伤用户）→ 方案（预处理 + 可插拔规则链 + 可配阈值 + 状态机 + 回滚）→ 结果（演示：真实轨迹通过 vs 伪造轨迹拦截；数据：P95 响应时间、规则命中分布）→ 教训（阈值要数据驱动，不能拍脑袋）。

### 追问应对表（诚实版答案）

| 追问 | 怎么答 |
| --- | --- |
| 为什么不做微服务？ | 单人项目微服务是负担；模块化保留拆分点。讲清"什么信号出现才拆"（校验引擎独立扩容/灰度） |
| 误判了怎么办？ | 申诉通道 + 人工复核 + 阈值可配；用误判率数据调参（这是设计，不是已上线数据） |
| 校验算法是自己发明的吗？ | 是简化实现：漂移过滤/速度阈值是公开思路，我实现并组合成规则链；真实工业界还有道路拓扑校准（需要地图数据，未实现） |
| 怎么证明它有效？ | 测试集：真实轨迹 vs 伪造轨迹，给出拦截率/误判率（我造的测试数据） |
| 为什么不用现成规则引擎？ | 规则数量可控，自研更轻、可测、可配 |
| 并发下榜单会错吗？ | 乐观锁 + 贡献快照 + 回滚；讲写放大/读放大权衡 |
| 这里为什么不加 MQ/缓存？ | 没到量；加的话加在哪、解决什么——能说出"何时才需要"即可 |

### 诚实边界（必须守住）
- 只说你实现的：校验闭环、状态机、榜单回滚、测试。
- 你设计的没说实现的：四层审核漏斗、信用分、赛事支付——主动声明"这是整体方案设计，非本次实现"。
- 绝对不说的：这 146 页文档是你做的实现、支付已接入、微服务已上线。
