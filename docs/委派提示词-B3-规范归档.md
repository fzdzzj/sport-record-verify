## 派发前必须知道的 3 个机械规则（每条提示词都依赖）

**规则 1：主规范的三个改动位置**
- 顶部 `## 本规范已归档以下提案` 列表 → 追加一行 `- <change-id>（<中文名>）`
- 按能力域**新增 `## <域>` 段落**（格式与既有段落一致），放在 `## 变更历史` **之前**
- 末尾 `## 变更历史` 的 bullet 列表 → 追加一条，把 spec-delta 里 `## 备注` 中有价值的上下文写成「一句话决策 + 依据文档」的口径

**规则 2：ADDED vs MODIFIED 的处理不同**
- `## ADDED Requirements` → 需求整段搬入主规范对应能力域段落
- `## MODIFIED Requirements` → **不是追加**，而是**改写主规范里那条既有需求**。本批只有 `add-mapmatch-service` 带 MODIFIED（改「服务划分」：5 服务 → 6 服务），提示词 ② 专门处理

**规则 3：归档动作 = 移目录 + 回写状态**
```
git mv spec/changes/<change-id> spec/changes/archive/<change-id>
```
并把 `tasks.json` 里每个 task 的 `steps[].completed` 与 `passes` 回写为 `true`（当前 5 个提案全是 `false`，是历史遗漏）。
> 口径说明（写进提示词，别让子 agent 自己猜）：「已归档」的定义 = 代码在 main + 编译测试绿 + 文件移到 archive + 本提案的 spec-delta 已合并进主规范。四项缺一，不许标 `passes: true`。

**规则 4：主规范尾部「变更历史」现存 8 条，追加时保持排版一致（`- **<change-id>**：...`）**
