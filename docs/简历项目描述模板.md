## 0. 结论先行：深度够不够？

**够，而且超出多数简历项目。** 对标国内 Java 后端简历的常见项目深度：

| 档位 | 典型项目 | 架构 | 技术密度 | 差异化 |
| --- | --- | --- | --- | --- |
| 底层 | CRUD 管理系统 | 单体 | Spring Boot + MyBatis + MySQL | 无 |
| 主流（最泛滥） | 黑马点评类 | 单体 | Redis 全家桶（缓存/锁/秒杀/Feed/UV） | 弱 |
| 上档 | 电商/支付/订单类 | 微服务 | 状态机、幂等、MQ 削峰、分库分表 | 中 |
| **本项目** | **运动记录真实性校验（反作弊风控）** | **4 微服务** | **分库分表 + 限流熔断 + 消息事件 + 分布式锁 + 二级缓存 + 灰度 + 幂等 + 状态机回滚** | **强（自研校验规则链）** |

- 架构与技术密度已达"电商微服务"上档；差异化（自研规则链算法）超过绝大多数简历项目。
- **短板不是深度，是三点**：① 量化数据（拦截率/误判率/P95/压测）必须真实做出来（W7/W8）；② 叙事要包装成"反作弊风控"而非"运动 App 后端"——风控是简历/面试高含金量题材；③ 简历呈现用"挑战→方案→收益"，不是堆技术名词。
- **警告：不要再加技术了。** 深度已够，继续堆（ES/Seata 实现/K8s）边际收益为负，只增加被追问的风险。

## 1. 简历条目（直接可用，按"挑战→方案→收益"三段式）

> **运动记录真实性校验系统（反作弊风控）｜ 后端独立开发**
>
> **挑战**：运动社区平台存在刷里程、伪造轨迹等作弊行为，需在秒级判定运动记录真实性，且不能误伤真实用户。
>
> **方案**：
> - 设计 4 服务微服务架构（Spring Cloud Alibaba：Nacos 注册/配置、Gateway、OpenFeign），按边界拆分网关/用户/记录/校验；
> - **自研可配置规则链校验引擎**：漂移过滤 + 速度/加速度/停留/距离一致性规则，阈值 Nacos 配置 + **用户比例灰度**，异常秒回滚；
> - **审核状态机 + 改判回滚**：榜单仅累计通过记录，贡献快照表 + 乐观锁，驳回自动回滚；
> - 轨迹点**分库分表**（ShardingSphere-JDBC，user_id 分片）；点赞**读热写冷**（Redis 计数 + 异步落库）；**RocketMQ 事件解耦** + 消费幂等；**Redisson 分布式锁**（好友并发互加、定时任务防重）；**Sentinel** 网关限流 + 校验服务熔断降级；Caffeine+Redis 二级缓存（规则阈值）。
>
> **收益**：真实轨迹通过率 95%+，伪造轨迹拦截率 90%+（测试集 200 条，正负样本各半）；核心链路 P95 < 200ms；4 服务 Docker Compose 一键部署（附公网演示地址）。

## 2. 制造"追问点"（写进简历引导面试官深挖的 5 个点）

1. **误判 vs 漏判权衡**——阈值怎么定、怎么用测试集调（弹药 A）；
2. **为什么不需要分布式事务**——状态机 + 幂等 + 补偿 vs Seata（弹药 B）；
3. **分片键为什么选 user_id**——按单用户访问路由单分片、跨分片查询代价（弹药 H）；
4. **主链路同步、事件异步的边界**——什么时候才上 MQ（弹药 D）；
5. **规则灰度怎么回滚**——版本 + 比例 + 误判率对比（弹药 J）。

## 3. 必须真实做出来的量化数据（W7/W8 产出，写进简历）

| 数据项 | 怎么来 | 目标 |
| --- | --- | --- |
| 测试集规模 | 真实 GPX（自己跑 + 公开数据集）+ 伪造脚本（匀速/抖动/飞点/折返） | ≥200 条，正负各半 |
| 拦截率 | 伪造样本被 reject 的比例 | ≥90% |
| 误判率 | 真实样本被 reject 的比例 | ≤5% |
| P95 响应时间 | 主链路压测 | <200ms |
| 压测 QPS | 简单压测（JMeter/自写） | 记录真实数字即可，不虚标 |

## 6. 避坑（对照简历方法论）

- 不写"精通/熟悉 xx"堆砌；每个技术点配一句"用在哪个场景解决了什么"；
- 不写"负责接口开发"；写"解决了什么、结果如何"；
- 不写 146 页文档；项目经历只占简历 1/4 页，其余靠面试讲；
- 诚实边界：前端是 AI 辅助生成、微服务是单人实践——被问到时如实说明并讲清边界（见执行计划第 5 节）。
