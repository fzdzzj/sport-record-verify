## 1. 一句话：这个变更做了什么

给系统加上了「**点赞**」能力：用户可对**通过校验（PASSED）**的运动记录点赞/取消，并查看点赞数与是否已赞。
核心卖点是**读热写冷 + 最终一致**：

1. **点赞/取消走 Redis**（原子 INCR/DECR + 成员集判重），微秒级完成、不碰 DB —— 与校验主链路（P95<200ms）解耦；
2. **落库走异步批量**：点赞/取消只往 Redis 队列写一条 pending 操作，定时任务（5s）批量 flush 到 `record_like`，
   用 Redisson 锁 `lock:like:flush`（30s 看门狗）保证**多实例仅一个执行**；
3. **对账兜底**：低频任务以 `record_like` 行为权威源纠正 Redis 计数并重建成员集，进程重启也不怕漂移。

之前 `record_like` 表建好了但没人写、Redis 计数没人用；这次把「点赞 → 计数 → 异步落库 → 对账」整条链路补齐，
并为后续排行榜变更（好友榜按点赞排序）铺好了 Feign 契约。

## 3. 对外接口（谁调用、传什么、拿什么）

外部统一走网关 `http://localhost:8080`；内部服务间走 `/internal`（Feign，`RecordApi` 点赞三方法）。

### 3.1 点赞

```
POST /record/api/records/{id}/like        （网关路径；服务直连为 /api/records/{id}/like）
Body: { "userId": 1001 }                  ← 点赞人（骨架无鉴权，调用方显式携带）
成功: 200 { "code": 0, "data": { "recordId": 1, "likeCount": 3, "liked": true } }
失败: 3001 记录不存在 ｜ 6001 记录未通过校验，不可点赞（REJECTED/VERIFYING/SUBMITTED）
```

> ⚠️ 与规范的说明：审批版 §4.6 未定义点赞请求体。因骨架没有登录鉴权，沿用 record 域惯例由调用方显式带 `userId`
> （后续接 JWT 后改从 token 解析）。重复点赞返回当前状态且**计数不变**（幂等）。

### 3.2 取消点赞

```
DELETE /record/api/records/{id}/like?userId=1001
成功: 200 { "code": 0, "data": { "recordId": 1, "likeCount": 2, "liked": false } }
失败: 3001 记录不存在
```

- 重复取消返回当前状态且计数不变（幂等）；
- 取消**不校验 PASSED**：记录事后被驳回也应允许收回点赞；
- 计数 DECR 有**下限 0**，漂移/并发下不会出现负数。

### 3.3 查询点赞状态

```
GET /record/api/records/{id}/like?userId=1001
成功: 200 { "code": 0, "data": { "recordId": 1, "likeCount": 3, "liked": true } }
```

- 计数优先读 Redis（读热写冷），键缺失时兜底 `COUNT(*)` 并回填，不会读到冷启动的 0 假象；
- `liked` 走成员集 SISMEMBER，即「是否已赞」。

### 3.4 错误码速查

| 错误码 | 含义 | 触发场景 |
| --- | --- | --- |
| 3001 | 记录不存在 | 点赞/取消/查询时记录 id 不存在 |
| 6001 | 记录未通过校验，不可点赞 | 对 REJECTED / VERIFYING / SUBMITTED 记录点赞 |
| 400 | 参数错误 | userId 缺失 |

## 4. 三个核心设计（面试弹药：为什么不会出问题）

### 4.1 Redis 成员集 = 点赞幂等的第一道闸门（T9）

- 点赞先 `SADD like:record:{recordId}:users {userId}`：返回 **1 = 首次** → 才 `INCR` + push pending；
  返回 **0 = 已赞** → 幂等跳过，计数不变、不重复落库；
- **SADD 是原子操作**：并发同人同赞只有一个赢家（返回 1 者负责计数），从根上杜绝重复 +1；
- 取消同理走 `SREM`，返回 0 视为未赞 → 幂等。

### 4.2 联合主键 = 物理层兜底（双保险）

- `record_like` 主键 `(record_id, user_id)`（审批版 §6.2 已建）：无论业务层怎么并发，
  数据库只允许一行存在；
- flush 用 **INSERT IGNORE**：撞主键冲突的行自动跳过，不报错不重复；
- 业务层成员集 + 物理层主键，**任意一层失效都由另一层兜住**——这就是「重复点赞幂等」的双保险。

### 4.3 读热写冷 + 异步批量落库 + 对账 = 最终一致

- **写路径**（点赞/取消）：纯 Redis 操作（INCR/DECR + SADD/SREM + RPUSH pending），微秒级，不碰 DB，
  与校验主链路解耦；
- **落库路径**：`@Scheduled` 每 5s 触发 `flushPendingLikes`，Redisson 锁 `lock:like:flush`
  （lease=-1 → 默认 **30s 看门狗**自动续期，审批版 §7.5 定时任务防重同款）保证多实例仅一个执行；
  批量落库 **成功才 LTRIM** 消费队列，失败整批保留重试——且 flush 本身幂等
  （INSERT IGNORE 撞主键跳过、DELETE 无行可删）；
- **对账路径**：每 10min 以 `record_like` 行为**权威源**，覆盖 Redis 计数并重建成员集
  （进程重启丢 Redis 计数/成员集后的兜底收敛）；
- 口径：**计数权威源是 DB 行，Redis 只是读热写冷的加速层**，两者最终一致。

## 7. 如何自己验证（起栈后四步）

前置：`docker compose up -d` 起中间件，然后启动 record-service + gateway。
先造一条 PASSED 记录（当前没有注册/提交入口联动演示时可直接插表）：

```sql
INSERT INTO record_db.sport_record (request_id, user_id, sport_type, status, version, created_at)
VALUES ('like-demo-001', 1, 1, 2, 0, NOW());   -- status=2 即 PASSED，假设得到 id=1
```

```bash
# 1. 点赞（首次 → 计数 1）
curl -X POST http://localhost:8080/record/api/records/1/like \
  -H 'Content-Type: application/json' -d '{"userId":1001}'
# → data.likeCount = 1, data.liked = true

# 2. T9 重复点赞（幂等 → 计数仍 1，落库仅一条）
curl -X POST http://localhost:8080/record/api/records/1/like \
  -H 'Content-Type: application/json' -d '{"userId":1001}'
# → data.likeCount = 1（不变）

# 3. 查点赞状态（读热写冷）
curl 'http://localhost:8080/record/api/records/1/like?userId=1001'
# → data.likeCount = 1, data.liked = true

# 4. 取消点赞（计数 0）+ 重复取消幂等
curl -X DELETE 'http://localhost:8080/record/api/records/1/like?userId=1001'
# → data.likeCount = 0, data.liked = false
curl -X DELETE 'http://localhost:8080/record/api/records/1/like?userId=1001'
# → 仍 0（幂等）

# 5. 未通过记录应被拒（再插一条 status=3 的记录 id=2）
curl -X POST http://localhost:8080/record/api/records/2/like \
  -H 'Content-Type: application/json' -d '{"userId":1001}'
# → { "code": 6001, "message": "记录未通过校验，不可点赞" }

# （落库核对：flush 触发后）
SELECT * FROM record_db.record_like;   -- 每个 (record_id,user_id) 最多一行
```

## 8. 遗留事项

1. **网关端到端冒烟**（tasks.json 任务 6 第 5 步）：需 docker 中间件环境，业务逻辑已由单测覆盖；
2. **并发同人同赞**未做并发单测：SADD 原子性在 Redis 侧保证（返回 1 者唯一计数），
   与好友模块「并发互加」用锁不同，点赞场景**无需锁**——这是本题的面试点（原子操作替代分布式锁）；
3. **对账扫描全表 DISTINCT**：演示规模（千级记录）直接全扫即可；生产可改增量游标/位图；
4. 点赞数未接入「记录详情」接口（当前没有外部详情端点）：计数查询由 `GET /like` 独立提供，
   待详情接口出现时直接把 `LikeDTO` 字段并入即可；
5. **pending 队列在 Redis**：进程重启后队列仍在（可重放），对账任务兜底极端丢失场景。
