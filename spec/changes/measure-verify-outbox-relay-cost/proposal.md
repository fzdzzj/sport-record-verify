# TASK-145 提案：分离 verify outbox relay 批内成本与调度空档

## Why

TASK-144 在 HEAD `28d277709d8020f49c6cff018652d1fe7c80975f` 前的同 jar、c100×2000 A-B-B-A 试验中，A=5000ms 两轮 `callback→SENT` P50 约 56.8/59.3s，B=500ms 两轮约 19.8/18.3s；B 的净投递速率约 35.6/37.3 行/s，A 约 15.2/14.7 行/s。但 A1 QPS 偏离预注册门槛且出现 2 次消费失败/重投，CPU/GC/DB/MQ 资源没有逐轮采样；结论是**未定/不推荐，不改默认 5000ms**，不能事后放宽门槛。

**最强反例**：B 轮 2010 条 outbox 的创建集中在约 22s，SENT 覆盖约 54～56s；有限突发能最终排空，不能证明长期到达率下不会持续积压。短间隔还可能增加空轮查询和 DB/MQ 压力。`VerifyOutboxRelay` 当前逐行 `syncSend` 后逐行 `markSent`，但现有日志不能分离取批、发送、标记、失败处理与锁内其他开销。`syncSend` 所计的墙钟包含序列化、网络/代理与确认，`markSent` 所计也可能包含获取连接/客户端等待；不能将它们直接称为纯 MQ 或纯 SQL。TASK-144 的日志分组不等同于真实调度周期。

**目的**：在不改变投递行为、默认调度和业务参数的前提下，用有界、默认关闭的诊断与同 jar 的两次有限突发测量，确定下一项应调查的占比最高因素，并明确尚不能证明的持续吞吐。此项只测量、不推出默认值变更，也不以两轮数据宣称可复现的 A/B 收益。

## What Changes

1. 冻结 HEAD/脏项并核对 TASK-143/144 原始数据、`VerifyOutboxRelay`、启动配置来源和停栈状态。审查同 run 关联、日志时钟、库表状态以及无自动清理等反例；旧报告仅作线索，不当作本次重复轮次。
2. 对 relay 添加**默认关闭的、仅诊断使用**的批次计时：`tryLock`、`selectPendingBatch`、循环内 `syncSend` 合计、`markSent` 合计、`incrRetry` 合计、锁持有总墙钟与本轮行数/成功/失败/耗尽；使用单调时钟，固定低基数字段，每个非空批次最多一条摘要日志。空轮及锁竞争计数也须以有界频率汇总，不输出 payload、eventId、令牌或逐行标识，不留无界驻留样本。保持原异常/中断/解锁路径，配置关闭时不增加批次日志或额外 DB/MQ 调用。补纯单测覆盖开关、成功、失败、空批、锁竞争及原有语义；如第一次红为编译/契约红，须如实标明，不冒充行为红。
3. 加一份可复现的本机采集办法（脚本或明确命令），每轮以同一时间轴保存 verify 进程 CPU 累计增量、内存、GC 增量、MySQL 线程/连接或可取得的负载读数、MQ broker 可得读数与采样失败说明；只读、不采集密钥、不混用全局累计值与单轮值。若某资源无法采集，标未知，不能填“无回归”。采样/计时开销本身未知，不与 TASK-144 计时关闭的数值直接做因果比较。
4. 先让诊断单测及 `bash scripts/verify/mvn-verify.sh --mode=offline --pl verify-service test` 通过，必要时 `package`，确认 jar 指纹。若健康、磁盘与中间件满足条件，最多两轮同 jar c100×2000：A=5000ms、B=500ms（仅启动覆盖 B 参数，均开启同一诊断），每臂可做相同的至多 c10×100 预条件化并排空，预条件化不得计入样本；测量前可投递 PENDING=0，耗尽待人工另列，测量后等待排空。每个失败/中止轮都计入两轮预算，不清库、不另加补跑；若首轮异常则直接收口为未覆盖，不凑第二轮。原始日志/采样存 gitignored `docs/perf/data/raw/`，记录起止时间、进程 PID、真实参数、提交请求形态、同 run recordId/eventId 配对覆盖率与可靠投递计数。
5. 按**同一周期**核对 `select+syncSend+markSent+incrRetry+剩余` 与锁持有总时长的闭合性，分别统计非空满批/短批/空轮及批间固定等待；区分周期内聚合与同 run 事件延迟，不相加独立 P50。对每轮报告创建/发送时间桶、可投递 PENDING 峰值/排空时间、同 run `callback→SENT` 分位与资源增量；明确本实验是有限突发，不能证明持续吞吐。若两个周期的环节归因仍不可靠，保留“未分离”而不推断纯 MQ/纯 SQL/CPU 原因。
6. 交付报告与 JSON 摘要、三件套状态、TASK-145 spec/handoff、PLAN 和统一总览，核对实际改动清单、`git diff --check`、仓库无参数 mailbox 契约。仅提交本任务文件（必要时业务/台账两笔本地提交），不 push/PR；不借本任务改变默认 `relay-interval-ms`、批量、并发发送、重试、锁、SQL/索引、MQ、池或 JVM 参数。结论只选择**下一步单一待证因素**，不把诊断开启轮当生产默认收益。

## Impact

- 规范：`spec/specs/sport-record-verify/spec.md` 中 outbox 可靠投递和性能证据的增量测量约束；不修改业务契约。
- 预计代码：`verify-service/src/main/java/com/sportverify/verify/mq/VerifyOutboxRelay.java`，对应单元测试；必要时新增同包有界诊断辅助类与测试。不修改生产 YAML、Mapper SQL、消息载荷、事件状态或数据库结构。
- 预计工具/文档：可选 `scripts/perf/` 的只读采样脚本，`docs/perf/` 报告/摘要、此三件套、TASK-145 两件套、`work/mailbox/PLAN.md` 与统一总览。raw/log 不入库。
- 数据：最多 2×(2000+10) 个测量请求，外加每臂至多 100 个预条件化请求；对应轨迹数据会写入**现有演示库**且不自动清理。运行前须确认磁盘、服务和数据卷安全；若不可接受，停止并报告未覆盖。
- 覆盖：仅四服务局部（如 leaderboard/mapmatch 未起）；SENT 不是榜单消费完成；不以此代替真中间件 IT、online/CI 或 R5 质量验收。

## 停止条件与判定边界

- 环境、服务健康、参数来源、时间关联、资源采集或磁盘安全不明时停；诊断明显影响路径正确性/日志洪泛/引入额外远程调用时先修诊断且不得强行压测。
- 出现失败、重投、关联缺口、异常增长的积压或资源压力，停止进一步轮次，保留原始证据和错误，不用后验解释丢弃样本。
- 仅凭两轮不能判候选有可复现收益；即便 B 更快，也不得在 TASK-145 更改 5000ms 默认值。若下一步需默认值决策，须另立包含重复、可比性、资源和更长稳态检验的提案。
