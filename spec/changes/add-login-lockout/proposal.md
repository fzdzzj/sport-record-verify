# 提案：落地账号锁定（登录爆破防护闭环）

## Why

JWT 鉴权闭环（add-jwt-auth）已实现注册/登录/双 token/网关鉴权/数据隔离，但**登录爆破防护只做了一半**：`AuthService.countFailure` 已经做了失败计数（Redis INCR + 15min TTL 窗口 + 阈值告警），但达到阈值后**只 `log.warn`，不真正锁定**——登录流程照样继续校验密码。攻击者可以无限重试撞库，失败计数形同虚设。这是安全闭环的最后一块缺口。

**背景**：
- 审批版 §4.1「登录：错密码 → 401 并计失败（窗口限频 + 失败锁定，讲设计）」——「失败锁定」此前一直是讲设计。
- `AuthService` 已有 `FAIL_KEY_PREFIX`/`FAIL_COOLDOWN_MINUTES=15`/`FAIL_THRESHOLD=5` 三个常量，注释明确写「锁定落地属后续变更」。
- 代码已含失败计数 + 登录成功清计数 + 阈值告警，只差「达阈值后拒绝登录」这一步。

**当前状态**：失败计数与告警已实现；达阈值后登录仍继续校验密码；无锁定状态、无锁定时长、无「已锁定」的明确错误语义。

**期望状态**：同一手机号在窗口期（15min）内连续失败 ≥5 次 → 后续登录请求直接拒绝（不校验密码，防撞库 + 省 BCrypt 计算），返回明确「账号已临时锁定」；锁定期过后自动解锁；登录成功即清零计数。锁定策略可配（开关、阈值、窗口、锁定时长）。

## What Changes

- **锁定状态**：复用现有 `auth:fail:{phone}` 计数键，达到阈值后再写一个 `auth:lock:{phone}` 锁定键（TTL = 锁定时长），或复用计数键的 TTL 作为锁定窗口。
- **登录前置检查**：`AuthService.login` 入口先查 `auth:lock:{phone}` 是否存在 → 存在则直接抛「账号已临时锁定」（403 或 429，不校验密码、不消耗 BCrypt）。
- **失败触发锁定**：`countFailure` 达阈值时，除告警外写锁定键（TTL = 锁定时长），并记录锁定日志。
- **成功清零**：登录成功同时删除计数键与锁定键（现有已删计数键，补删锁定键）。
- **配置化**：`app.auth.lock.*`（enabled、threshold、window-minutes、lock-minutes），默认启用、阈值 5、窗口 15min、锁定 15min。
- **错误语义**：新增或复用错误码——建议复用 1002（FORBIDDEN）配「账号已临时锁定，请稍后重试」，或新增专用码；避免与「密码错误」混淆。

## Impact

### 受影响的规范
- `spec/specs/sport-record-verify/spec.md` - 追加账号锁定能力域需求（ADDED）：失败计数、锁定、自动解锁、成功清零。

### 受影响的代码
- `user-service`：`AuthService`（登录前置检查、失败触发锁定、成功清零）、`application.yml`（lock 配置）、`ResultCode`（如需新错误码）
- `api`：无（错误语义在错误码层）

### 用户影响
- 连续输错密码达阈值的用户会被临时锁定（防爆破），正常用户不受影响。

### API 变更
- 无新增端点；登录失败时错误码/语义可能变化（达阈值后返回「已锁定」而非「密码错误」）。

## 时间线评估

较小：约 0.5 周（安全收尾，改动集中在一个类）。

## 风险

- **误锁正常用户**（手抖多次输错）→ 缓解：锁定时长短（默认 15min）+ 窗口滚动重置；提供「忘记密码」讲设计（本项目无邮件验证）。
- **锁定键与计数键 TTL 不一致导致提前/延后解锁** → 缓解：统一 TTL 管理，锁定键 TTL = 锁定时长，计数键 TTL = 窗口，两者独立语义清晰。
- **Redis 抖动导致锁定失效** → 缓解：锁定是「安全增强」非「强一致必须」，Redis 异常降级为「不锁定但继续计数告警」（不因 Redis 故障阻止登录）。
- **错误语义混淆** → 缓解：锁定返回「账号已临时锁定」明确区分「密码错误」，避免攻击者据此探测账号状态（锁定状态本就该公开，反而阻断爆破）。
