# 提案：跨请求提交聚合先闸门、先复测（先不写聚合器）

## Why

压测报告 §10 后续项 2 把「提交侧批量聚合」与刷盘并列，当作吞吐天花板。跨请求聚合（把多个用户的 submit 攒成一批再写库）会改变延迟语义和失败边界，比「一条记录内批量 INSERT」危险得多。

当前连「单记录批量 INSERT」都还不是默认（另案）。没有「默认优化路径上的新 QPS」就做跨请求聚合，是把未测量的方案当优化。

**背景**：
- 单记录批量 INSERT 已有 3.9× 实证。
- 跨请求聚合没有实测，也没有开关。

**当前状态**：每个 submit 请求同步写自己的记录+轨迹。

**期望状态**：本变更新增「何时才允许做跨请求聚合」的闸门：必须先在批量 INSERT 默认开启下复测 100 并发 QPS/P95；若仍是连接占用主导再单开实现变更。本变更**不实现聚合器**。

## What Changes

- ADR-0002 / 压测报告后续项改写：跨请求聚合 = 未开门，前置是默认批量 INSERT + 复测 CSV。
- `scripts/perf` 复现说明补一句：优化档必须 `batch-insert-enabled=true`（或依赖另案默认）。
- 不改 submit 业务代码。

**明确不做**：不实现请求缓冲队列、不合并不同 request_id、不改接口语义。

## 风险

- **被理解成已经做了聚合** → 缓解：提案标题和规范都写「不实现」。
- **与默认开批量混成一个变更** → 缓解：分目录，禁止改 application.properties。
