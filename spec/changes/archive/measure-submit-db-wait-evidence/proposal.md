# 提案：提交链路 DB 等待归因与重复负载核验

## Why

TASK-139 在单次同负载复测中观察到 QPS 120.90→123.23、P50 777.55→711.45ms，同时 P95 1188.55→1332.35ms。工程改动已经收口，但现有报告把 `select` 段 681.6ms 中的池等待称为“直接证实约 92%”，把 `beforeCommit→afterCommit` 的 28.9ms 全部称为 fsync 地板，并依据一次未改行为的 split 跑次将 P95 +12.1% 归为噪声。这些超出了当前计时点能证明的范围：`select` 包含连接池等待与查询等开销；提交段也不等于纯 fsync；现有负载是单次前、单次后，且 TASK-139 同时删一次 UPDATE、关闭 SQL 展示，不能分别归因收益。

**已验证的本地事实**：当前服务底层连接池由 `record-service/src/main/resources/sharding.yaml` 中 ShardingSphere YAML 配置的 HikariDataSource 创建；`ShardingDataSourceConfig` 将 YAML 交给 ShardingSphere 工厂，Spring Bean 是代理 DataSource；record-service 已有 Actuator 与 Prometheus 依赖；`SubmitTxTiming` 默认关闭，但开启后在单例内长期累积每次提交的段样本，没有容量上限。以上都不等于“已有可用且按提交请求归属的 Hikari 等待指标”。

**本轮目标**：纠正历史归因的证据等级；在不改变业务路径的前提下，验证能否把物理连接获取等待、SQL/JDBC 调用与提交过程分别量到；用少量重复的同一负载记录波动范围。只有测量机制确实可证，才能升级相应结论；否则明确“未分离测得”。本轮不实施下一项性能优化。

## What Changes

1. 在既有 TASK-139 复测文档、原始摘要 JSON 和 handoff 追加更正说明，不删除原始数字：681.6ms 是混合段；各段独立 P50 不能直接相加当作同一请求的 P50；28.9ms 是提交区间而非 fsync 单项；前后变化是单次观察，不宣称 P95 噪声已证实、收益已归因于某一个改动。必要时给 TASK-138 归因文档补交叉引用，不改历史原始数据。
2. 先只读检查现有 `/actuator/metrics` 或 Prometheus 是否实际暴露**内层** Hikari 物理连接获取等待、池活跃/等待线程指标，并核实指标所属数据源、采样口径和其他后台任务是否混入。Spring 外层代理 Bean 的指标不得冒称底层 Hikari 指标；JMX 待连接线程数快照也不能代替单请求等待时长。
3. 若现有指标不足，可做一个**默认关闭、作用域受控**的最小诊断插桩，位置必须能分别观测实际物理连接获取、SQL/JDBC 执行、事务提交区间；记录每个计时点的起止边界、关联方式和遗漏路径，并以单测证明关闭态不改变业务、回滚不记成功样本、开启态内存有界。不要以整段 `select` 减去未经验证的常数推算“直接测得的池等待”。如在允许范围内无法可靠分离，不扩大依赖或侵入 ShardingSphere 私有接口：停止该项，记录技术阻碍与未覆盖。
4. 环境与容量允许时，用当前同一 HEAD/配置/样本、`load 100 2000` 重复最多两次，并与 TASK-139 已有 `dbfoot` 跑次组成三轮；若旧跑次的环境指纹或原始文件不匹配，最多再补一次。**本作业新增负载总数不超过三次**，任何开启额外诊断开关的跑次也计入上限，但不得与计时关闭跑次混为同组。无法分离池等待不妨碍记录当前版本的延迟波动，只妨碍请求级归因。每轮独立 label，原始数据留在既有 gitignore 的 raw 目录；禁止把 split（计时开启）当作计时关闭的同组复测。先核对剩余磁盘和预计新增轨迹行数（每轮约 2000×300 点）；不足则不跑、不清库，记未覆盖。报告各轮 QPS/P50/P95/P99/错误率与环境指纹及范围，不规定“必然改善”。
5. 收口时只给出下一步一个瓶颈假设及其证据等级；若归因仍不足，下一步是补观测而不是盲调池或刷盘。本作业统一完成必要的单测、验证、台账/契约与本地提交；不得拆成多轮索要单个 commit/命令，未经授权不 push/建 PR。

## 风险

- ShardingSphere 内层池可能不经 Spring Actuator 的常规 DataSource 自动绑定；先实测指标存在性/归属，再选插桩位置，禁止假定指标已存在。
- 打开现有 `SubmitTxTiming` 会持续保存每个样本；若复用则改成有界结构并验证内存上限，绝不为了诊断引入生产无界缓存。
- 多次 300 点请求产生大量持久数据与磁盘写入；只在容量足够时运行，不清理演示库或 Docker 卷，不并行启动多套服务。
