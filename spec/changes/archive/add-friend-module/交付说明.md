## 1. 一句话：这个变更做了什么

给系统加上了「**双向好友**」能力：A 向 B 发好友申请 → B 同意 → 两人互相出现在对方好友列表里。
同时从**根上解决两个并发/重复问题**：

1. **并发互加**（A、B 同时互发申请）只会产生**一条**好友关系 —— 靠 Redisson 分布式锁 + 规范化存储双保险；
2. **重复申请/已存在关系**会被幂等拦截，返回 5001，不建第二条单。

之前 user-service 只有健康检查端点，`friend_request` / `friendship` 两张表建好了但没人写；这次把
「申请 → 同意/拒绝 → 列表」整条链路补齐，并为后续 record-service 的「好友榜」铺好了 Feign 契约。

## 3. 对外接口（谁调用、传什么、拿什么）

外部统一走网关 `http://localhost:8080`；内部服务间走 `/internal`（Feign）。

### 3.1 发起好友申请

```
POST /user/api/friends/requests        （网关路径；服务直连为 /api/friends/requests）
Body: { "userId": 1001, "targetUserId": 1002 }      ← 申请人、被申请人
成功: 200 { "code": 0, "data": { "id": 5, "fromUser": 1001, "toUser": 1002, "status": "PENDING" } }
失败: 2002 用户不存在 ｜ 5001 重复申请/已存在关系 ｜ 400 自申请或参数缺失
```

> ⚠️ 与规范的说明：spec 示例请求体只有 `{targetUserId}`。由于骨架没有登录鉴权，
> 系统无法知道「是谁在申请」，所以沿用 record 域惯例，由调用方显式带上 `userId`（后续接 JWT 后改从 token 解析）。

### 3.2 同意申请（目标用户操作）

```
POST /user/api/friends/requests/{id}/accept
成功: 200 { "code": 0, "data": { "id": 5, "fromUser": 1001, "toUser": 1002, "status": "ACCEPTED" } }
     （同时写入 friendship 关系：双方从此互见）
失败: 5002 申请不存在或已处理（非 PENDING 不允许流转）
```

### 3.3 拒绝申请

```
POST /user/api/friends/requests/{id}/reject
成功: 200 { ..., "status": "REJECTED" }   （不写 friendship）
失败: 5002（同上）
```

### 3.4 好友列表

```
GET /user/api/friends?userId=1001&page=1&size=20
成功: 200 { "code": 0, "data": {
  "current": 1, "size": 20, "total": 2,
  "records": [ { "userId": 1002, "nickname": "小红", "createdAt": "..." }, ... ] } }
```

- **只返回 ACCEPTED 的关系**（friendship 表本身只存已接受关系，天然排除 PENDING/REJECTED/CANCELLED）；
- 每个列表项已由 `(user_low, user_high)` 反规范化成「对方的 userId + 昵称」，调用方不用懂存储细节；
- 双向语义：A 查得到 B，B 查得到 A（同一行关系，双方各自还原出对方）。

### 3.5 错误码速查

| 错误码 | 含义 | 触发场景 |
| --- | --- | --- |
| 2002 | 用户不存在 | 申请时目标用户 id 不存在 |
| 400 | 参数错误 | 自申请、userId/targetUserId 缺失 |
| 5001 | 重复申请或已存在关系 | 同向 PENDING 重复 / 反向 PENDING 已存在 / 已是好友 |
| 5002 | 关系不存在 | 申请单不存在 / 对已处理（非 PENDING）申请再 accept、reject |

## 4. 三个核心设计（面试弹药：为什么不会出问题）

### 4.1 规范化存储 —— 从根上消灭「A-B / B-A 重复行」

- 好友关系**不按方向存**，永远存成 `(user_low, user_high)` 且强制 `user_low < user_high`；
- 数据库层：主键 `(user_low, user_high)` 唯一 + `CHECK (user_low < user_high)` 约束；
- 效果：`(1001,1002)` 与 `(1002,1001)` 在物理上是**同一行**，无论怎么并发写，数据库只允许一行存在；
- 反向重复插入会被主键拒绝，代码捕获 `DuplicateKeyException` 后按「幂等成功」处理，不报错不中断。

### 4.2 Redisson 分布式锁 —— 并发互加只产生一条

- 锁键：`lock:friend:{low}_{high}`，用 min/max 归一 → **A→B 和 B→A 抢的是同一把锁**；
- 锁内做「检查-建单」原子化：先查有没有同向/反向 PENDING、有没有既有关系，没有再插入；
- 10 秒租期（可重入锁），与 4.1 的数据库约束形成**双保险**：
  锁挡住「逻辑层重复」，主键挡住「物理层重复」；
- 同意/拒绝入口同样加锁，避免 accept 与建单交错。

### 4.3 乐观状态机 —— 并发 accept/reject 只有一个赢

- 状态流转不用「先读再写」，直接用
  `UPDATE friend_request SET status=新状态 WHERE id=? AND status=PENDING`；
- 影响行数 = 0 说明申请已被别人处理（或不存在）→ 返回 5002，天然防并发重复流转；
- 合法流转只有一条路径：`PENDING → ACCEPTED / REJECTED / CANCELLED`。

## 7. 如何自己验证（起栈后三步）

前置：`docker compose up -d` 起中间件，然后启动 user-service + gateway。

```sql
-- 1. 造两个用户（当前没有注册接口，直接插表；注意拿返回的自增 id）
INSERT INTO user_db.user (phone, password_hash, nickname, status, created_at)
VALUES ('13800000001', 'x', '小明', 1, NOW());
INSERT INTO user_db.user (phone, password_hash, nickname, status, created_at)
VALUES ('13800000002', 'x', '小红', 1, NOW());
-- 假设得到 id=1（小明）、id=2（小红）
```

```bash
# 2. 小明申请加小红（body 里带申请人 userId）
curl -X POST http://localhost:8080/user/api/friends/requests \
  -H 'Content-Type: application/json' -d '{"userId":1,"targetUserId":2}'
# → data.status = "PENDING"

# 3. 小红同意（申请单 id 取上一步返回的 id，如 1）
curl -X POST http://localhost:8080/user/api/friends/requests/1/accept
# → data.status = "ACCEPTED"

# 4. 双方列表互见（双向语义）
curl 'http://localhost:8080/user/api/friends?userId=1&page=1&size=20'   # 小红在列
curl 'http://localhost:8080/user/api/friends?userId=2&page=1&size=20'   # 小明在列

# 5. 重复申请应被拦截
curl -X POST http://localhost:8080/user/api/friends/requests \
  -H 'Content-Type: application/json' -d '{"userId":1,"targetUserId":2}'
# → { "code": 5001, "message": "你们已是好友" }
```
