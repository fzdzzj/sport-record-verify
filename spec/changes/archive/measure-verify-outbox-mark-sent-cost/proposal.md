# TASK-146 提案：校正 relay 诊断口径并拆解逐行 markSent 成本

## Why

TASK-145 在 HEAD `f1c9b6e46da641ab0079dba983aa2bf200d382f4` 的诊断开启、c100×2000 有限突发中，满批 `markSent` 外层 Mapper 调用墙钟中位约 1046/1037ms（100 行），占目前所记“锁内处理段”约 79.7%/71.4%。原始日志按批内配对比例复算也支持其为最大已测段；**这不是纯 SQL 耗时，也不是改善证据**。唯一待证因素是这一段内部究竟由连接获取、MyBatis/JDBC 执行、提交或其他客户端等待中的哪部分主导。不能仅凭 10ms/行就批量 UPDATE、调连接池、改调度或调 JVM。

先修两个会误导后续归因的反例：`markSent` 成功前后抛错时，当前 catch 从 `sendStart` 再累计 `sendNanos`，可把已经计过的发送和失败的标记过程重复归到发送；当前 `lockHoldMs` 在诊断日志和 `unlock()` 前截取，仅代表锁内处理段而非完整占锁时间。TASK-145 两轮失败数为 0，前一缺陷不推翻其成功路径数字；后一命名/周期闭合边界必须改正。

**最强反例**：每行 `markSent` 的约 10ms 是调用端混合墙钟，且 verify 进程还处理消费与回调；全局 MySQL 计数和 Hikari 汇总无法自动归因到 relay 的单行 UPDATE。额外包装数据源或打点可能改变运行时间甚至语义。若不能用有界、默认关闭的安全方式取得**同一次调用内可配对**的下层读数，应报告“内部构成未分离”，停止优化，不以分位数相减或全局差值臆断。

## What Changes

1. 先写失败注入判别测试，修正发送/标记计时互不重复；把现有 `lockHoldMs` 精确定义为锁内处理段，若要报完整占锁则在解锁后测量，并保持异常传播、重试、eventId、SENT、锁释放语义。默认关闭时不得增加 DB/MQ 调用和逐行日志；记录关闭态必要计时开销或将其去除。
2. 审查 verify-service 的 MyBatis→JDBC→Hikari 实际调用路径，选择最小且可证的嵌套计时点；只有能与 relay 同一次 `markSent` 调用配对的读数才能拆账。各层按“Mapper 调用墙钟／客户端 JDBC 执行墙钟／连接获取墙钟／未分离残差”等实际边界命名，不将客户端测量写成纯服务端 SQL、纯 fsync 或纯池等待。配置默认关闭，有界低基数聚合、异常安全清理，不记录事件 ID、payload、SQL 参数、用户标识或凭证。
3. 用单元判别和必要的轻量真 MySQL 集成证据验证开关、配对、非负/闭合、失败、空批、锁竞争、异常、资源释放与投递语义；若安全插桩不可行，保留正确的诊断口径，剩余内部构成标未知，不扩范围。
4. 条件满足时仅做**一轮**与 TASK-145 A 同形态的 c100×2000、默认 5000ms、诊断开启有限突发；同 run 分账和资源采集，原始证据留忽略目录。与 TASK-145 属不同 jar/诊断实现，**不得当作优化前后性能收益对照**。不清库，不额外补跑失败轮。
5. 同次作业完成报告、机器摘要、三件套勾选、TASK-146 台账、PLAN/机会总览、只改清单、契约和必要本地提交；不 push、不建 PR。
