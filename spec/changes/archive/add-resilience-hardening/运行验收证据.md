# 运行验收证据：容错硬化（add-resilience-hardening）

验收时间：2026-09-16；环境：六服务全部在跑（8080-8085）+ 中间件容器（MySQL 3307 / Redis 6379 / Nacos 8848 / RocketMQ 9876）。

本文件补齐 proposal 阶段 7 中「需本地起服务后手测」的运行时验收项（此前的 `mvn verify` 只覆盖单测）。

## 一、内部接口凭证（`/internal/**` 校验 `X-Internal-Token`）

| # | 调用方式 | 请求 | 实测响应 | 判定 |
| --- | --- | --- | --- | --- |
| 1 | 直连 8081 `POST /internal/auth/grant-admin`，**不带** token | `{"userId":99999999}` | `HTTP 403` `{"code":1002,"message":"无权限访问"}` | 通过（拒绝） |
| 2 | 同上，带**错误** token | `X-Internal-Token: wrong-token` | `HTTP 403` `{"code":1002}` | 通过（拒绝） |
| 3 | 同上，带**正确** token | `X-Internal-Token: local-demo-internal-token` | 通过过滤器 → 业务层 `HTTP 200` `{"code":2002,"message":"用户不存在"}` | 通过（放行至业务层） |
| 4 | 经网关 8080 `POST /internal/auth/grant-admin` | 带正确 token | `HTTP 404`（`requestId` 已注入） | 通过（网关无 internal 路由，死配置已裁） |
| 5 | 直连 8081 `GET /internal/health` 不带 token | — | `HTTP 403` `{"code":1002}`；带 token → `{"code":0,"data":"user-service is alive"}` | 通过（探活同口径） |

结论：直连端口不再裸奔；网关侧 `/internal/**` 无路由（404），删除的白名单项确为死配置。

## 二、好友榜降级（user-service 不可用 → 空榜，非 500）

先构造非空基线（临时插入好友关系 `1↔901`，验收后已删除，见文末清理）：

```
# user-service 在线
GET 8084 /api/leaderboard?type=friend&userId=1
{"code":0,"message":"success","data":[{"rank":1,"userId":901,"nickname":"用户901","distance":1963.7}]}   HTTP 200

# 停掉 user-service（kill 8081 监听进程）后同一请求
{"code":0,"message":"success","data":[]}   HTTP 200   耗时 0.027s
```

停服期间同一次响应里还可观察到**昵称兜底**（读路径软降级的直接证据）：

```
# user-service 在线：总榜昵称来自 user-service 批量查询
{"rank":2,"userId":1,"nickname":"????A","distance":1555.26}

# user-service 停机：昵称退化为占位符，榜单本体仍可用
{"rank":2,"userId":1,"nickname":"用户1","distance":1555.26}
```

重启 user-service 后：内部健康 `200`、好友榜恢复非空、总榜昵称恢复 `????A`、登录链路恢复 `1001`（凭据错误）。

结论：降级口径为**空榜 + 200**，不返回 500/堆栈、不泄露总榜非好友；依赖恢复后自动回到正常结果，无需人工干预。

## 三、附带发现：`user_db` 迁移未落库导致登录 500（**已修**）

验收判据 3 首次执行时返回 `HTTP 500 {"code":9999}`，日志根因：

```
Caused by: java.sql.SQLSyntaxErrorException: Unknown column 'role' in 'field list'
```

- `user_db.user` 实表缺 `role` 列（`sql/01-user-db.sql` 已含该列，故**全新建库正常、存量库静默损坏**）。
- 影响面不止内部接口：`AuthService.login` 同样按实体查 `role`，**登录接口一并 500**（实测 `POST /api/login` → `code:9999`）。
- 单测全绿是因为 mapper 被 mock，CI 抓不到 —— 典型「编译绿 ≠ 可运行」。
- 修复：执行仓库既有幂等迁移 `sql/migrations/add-user-role.sql`（`USE user_db;` 自包含，`information_schema` 判存）。执行后 `role` 列就位，登录恢复 `1001`、`grant-admin` 恢复 `2002`/成功。
- **根因在流程**：`sql/` 是「建表脚本（新装）」+ `sql/migrations/`（升级）双源，但 README「快速开始」只跑 `docker compose up -d`（initdb 仅首次生效），**没有任何入口告诉你存量库要跑迁移**。`add-admin-rbac` 的 proposal 里 `[x] 数据库迁移` 勾得体面，实际缺「升级执行入口」。建议单开变更补：迁移执行脚本 + README 升级说明 + 冒烟断言（详见后续提案）。

## 四、环境备注：`mvn verify` 与运行中服务互斥

`record-service` 在跑时执行 `mvn verify`，`spring-boot:repackage` 会因 `target/*.jar` 被占用而**重命名失败**，且此时 `target/` 里只剩 thin jar（`BOOT-INF/lib` 条目为 0，**不可 `java -jar` 启动**），下次重启服务才会暴露。

- 本次验证改用 `mvn -B verify -Dspring-boot.repackage.skip=true` 规避（结果：`BUILD SUCCESS`，245 个测试全绿）。
- 若需重建可执行 jar：先停对应服务再 `mvn -B verify`（不要用 `clean`，服务占用同样会失败）。
