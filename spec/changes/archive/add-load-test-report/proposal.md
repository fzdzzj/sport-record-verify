# 提案：压测实录与优化报告

## Why

前 5 个变更（骨架+校验引擎+好友+点赞+排行榜）把功能闭环做完后，缺**证明系统可用性的真实数据**。大厂面试最认「真实数据 + 坑与优化实录」，交付标准（拦截率≥90%、真实通过率≥95%、P95<200ms）与附录 A1/A.3（100/500/1000 并发 + 至少 1 个优化案例）都需要本变更落地，产出可直接写进 README/ADR、可放进面试故事线的压测报告。这是整个项目的「面试弹药 A1」载体。

**背景**：
- 审批版 §8.2 延迟预算（网关 10ms + 落库 50ms + 校验 100ms + 事件异步，合计 ~160ms）、§8.3 可用性（Sentinel 限流 5k QPS、verify 熔断降级转人工）、§9 T12 量化目标、附录 A.3 压测方案均已定稿。
- 交付标准（§12.1 第 9 项、§12.3 第 9 项）：拦截率≥90%、真实通过率≥95%、P95<200ms、Compose 一键起。
- 已确认：不购云服务器，本地 Docker Compose 演示 + 录屏；GitHub 公开（README/ADR 需整洁完整）。

**当前状态**：功能已可跑（骨架真实冒烟通过），但无压测脚本、无性能数据、无瓶颈定位与优化、无优化前后对比、指标（90%/95%/200ms）未实测验证。

**期望状态**：产出可复现的压测方案 + 100/500/1000 并发实录（P95/QPS/错误率）+ 至少 1 个 Explain 慢查询案例 + 1 个 GC/连接池调优案例，形成优化前后对比，写入 README/ADR，并输出演示录屏。

## What Changes

- **压测工具与脚本**：自写并发脚本或 JMeter，对「提交记录」接口发起 100/500/1000 并发；记录 P95/QPS/错误率/TP99。
- **量化验收指标实测**：测试集 ≥200 条（正负各半），验证拦截率 ≥90%、真实通过率 ≥95%、校验 P95 <200ms。
- **瓶颈定位与优化**：至少产出 1 个 Explain 慢查询案例（SQL 加索引/改写前后对比）+ 1 个 GC/连接池调优案例（GC 日志、HikariCP/线程池参数前后对比）。
- **Sentinel 限流与熔断验证**：网关限流对齐 5k QPS 目标；停 verify-service 验证熔断降级「转人工」，主链路不挂（对应 T11）。
- **压测报告文档**：`docs/perf/压测报告.md`，含方案、环境、数据、图表、优化前后对比、结论。
- **ADR 补充**：新增 ADR `0002-压测与优化实录`，记录每次优化的因果（快照前后数据，供面试追问）。
- **README 更新**：补压测结果摘要与复现命令。
- **演示录屏预处理**：准备录屏脚本/清单（录制本身在部署变更，本提案只产出压测素材口径）。

中等：约 1 周（W8，对应执行计划「测试集与调参」）。

## 风险

- **本地资源有限（3-4GB）限制并发上限** → 缓解：诚实记录本地单机上限，并发档位按实际能力取 100/500/1000 或说明极限值；性能结论按环境标注，不夸大。
- **指标不达标（90%/95%/200ms）** → 缓解：定位瓶颈优化；若阈值本身过松则调参；最终以实测为准如实记录，面试时诚实讲取舍（诚实口径是既定规则）。
- **优化前后对比难以复现** → 缓解：压测脚本可重复执行，报告记录环境快照与参数，ADR 记录因果。
- **技术卡壳超时**（既定决策）→ 缓解：压测属 P1，若与主线抢进度，核心指标（90%/95%/200ms）优先测完，深度优化案例可后补。

## 备注
