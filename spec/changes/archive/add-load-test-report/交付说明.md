   双路补偿自愈）；网关 Sentinel 限流（路由级 QPS 5000 基线，429 统一响应）；
3. **沉淀文档**：`docs/perf/压测报告.md`（方案/环境/数据/对比/结论，逐请求 CSV/JSON 全留存）、
   `docs/adr/0002-压测与优化实录.md`（每步优化的因果）、README 压测摘要。

**核心数据**：拦截率 100%、真实通过率 100%（目标 90%/95%）；校验链路端到端 P50 20.3ms；
提交吞吐 35.5→136.8 QPS@100 并发（3.9×）；500 并发错误率 6.85%→0%；
Sentinel 实测 99.35% 超限拦截；熔断转人工全流程（含恢复自愈 30/30 收敛）闭环验证通过。

## 4. 关键设计（面试弹药）

1. **优化必须可回退**：批量插入是配置开关不是删代码——基线路径保留，`--record.track.batch-insert-enabled`
   一键切换，优化前后对比任何人可复现；
2. **限流管流量、熔断管依赖**：Sentinel 在网关挡超量请求（路由级 QPS），Resilience4j 在服务间
   挡依赖故障（失败率熔断 + 快速失败），不强行统一；
3. **转人工不是黑洞**：MANUAL_REVIEW 是终态但可自愈——verify_db 终判是唯一权威，
   record 状态向它收敛（reconcileCallback 对账 + 补偿重放），实测 30/30 自动回到终态；
4. **诚实口径**：P95 541ms 的突发排队成因拆解、1000 并发 13.25% 错误的单机上限、
   1g 固定堆反而放大单次停顿的权衡——全部如实记录，不挑好看的数字。

## 6. 首跑修复清单（本项目首次全栈真实运行）

1. **MQ 发布超时**：`mqbroker` 未加载挂载的 broker.conf（缺 `-c`），brokerIP1 不生效 → 修 compose 命令；
2. **消息不消费**：WSL2 cgroup v2 触发 JDK NPE → broker 加 `-XX:-UseContainerSupport`；
3. **healthcheck 永败**：镜像内无 `ss` → 改 bash `/dev/tcp`；
4. **3306 冲突**：compose + 四服务数据源端口参数化（`MYSQL_PORT`，默认不变）；
5. **user-service 起不来**：补 `@MapperScan`（单测不经过 Spring 装配，真实起栈才暴露）；
6. **ShardingSphere 数字占位 NFE**：`ShardingDataSourceConfig` 泛化 env 替换；
7. **慢判定 vs 熔断超时竞态**：verify 终判对账收敛 + 转人工自愈重放。

## 7. 遗留事项

1. 突发场景（0.3s 内 200 条）端到端尾部 ~0.5s：消费调度批处理粒度，改进项（consumeThreadMax/
   拉取批次/客户端限速）已记录未实施；
2. `innodb_flush_log_at_trx_commit` 等 MySQL 侧吞吐 knobs：记录不实施（属环境调参非业务代码）；
3. Sentinel 规则当前代码加载（重启生效），Nacos 动态数据源为后续变更；
4. 引擎阈值不分运动类型（骑行 6-8m/s 会被 R1 误拦）、R4 对闭环路线判无穷大（真实环形跑误拦）——
   测试集构造已按现引擎口径规避，阈值分级属引擎后续灰度变更；
5. GC 案例结论：批量插入保留（GC 频率 −47%），1g 固定堆不采纳（建议回退自适应 + MaxGCPauseMillis），
   优化档压测数据是在 1g 堆下采集的，报告已注明。
