## 1. 一句话：这个变更做了什么

给系统补上了「**排行榜**」——校验闭环（提交→校验→判定→申诉）的最后一环，把可信的 pass 里程沉淀为**总榜 + 好友榜**：

1. **事件驱动入榜**：record-service 新增独立消费组订阅 `record-verify-events` 的 VERIFIED/REJECTED 事件——
   VERIFIED → `ZINCRBY leaderboard:overall {+distance} {userId}` + 写 `leaderboard_contribution` 回滚锚点（record_id 主键，status=ACTIVE）；
   REJECTED（改判驳回/维持拒绝）→ 按锚点行 `ZINCRBY {-distance}` 精确扣回 + 锚点置 ROLLED_BACK；
2. **读走 Redis ZSet**：总榜 `ZREVRANGE` 秒级取前 N；好友榜 Feign 一次拉齐好友列表后内存过滤（不逐条远程调用）；
3. **定时结算兜底**：以 `leaderboard_contribution` ACTIVE 汇总为**权威源**纠偏 ZSet（ZADD 覆盖 + ZREM 残留），
   Redisson 锁 `lock:scheduler:leaderboard`（30s 看门狗）保证多实例仅一个执行；
4. **并发安全**：同一记录的入榜与回滚共用 `lock:rollback:{recordId}` 串行化，锚点行状态迁移走乐观 UPDATE，
   影响行数决定是否加分/扣分——重复事件（eventId 去重键过期后重放）天然幂等。

之前 `leaderboard_contribution` 表建好了但没人写、事件 topic 已定义但无榜单消费者；这次把
「判定事件 → 入榜 → 改判回滚 → 榜单查询 → 定时对账」整条链路补齐。

## 3. 对外接口（谁调用、传什么、拿什么）

外部统一走网关 `http://localhost:8080`；内部服务间走 `/internal`（Feign）。

### 3.1 总榜

```
GET /record/api/leaderboard?type=overall&size=50     （网关路径；服务直连为 /api/leaderboard）
成功: 200 { "code": 0, "data": [
  { "rank": 1, "userId": 100, "nickname": "阿强", "distance": 42.5 },
  { "rank": 2, "userId": 200, "nickname": "小美", "distance": 20.0 } ] }
非法 type → 400；昵称服务不可用 → 以「用户{id}」占位降级，榜单仍可用
```

### 3.2 好友榜

```
GET /record/api/leaderboard?type=friend&userId=200&size=50
成功: 200 { "code": 0, "data": [ ...仅好友，按里程降序... ] }
无好友 / 好友均无 pass 里程 / user-service 不可用 → 空榜（可用性优先）
缺 userId → 400
```

> ⚠️ 与规范的说明：审批版 §4.5 未定义「查询人」如何传递。骨架无登录鉴权，沿用点赞域惯例
> 由调用方显式携带 `userId`（总榜不需要；接 JWT 后改从 token 解析）。
> 好友榜不含本人——审批版口径是「按好友列表过滤，只显示好友」。

### 3.3 内部契约变更（api 模块）

| 契约 | 新增方法 | 用途 |
| --- | --- | --- |
| `RecordApi` | `GET /internal/leaderboard`（type/userId/size） | 榜单 Feign 契约（与公开端点共用 `LeaderboardService`） |
| `UserApi` | `GET /internal/users?ids=`（批量用户概要） | 总榜前 N 名一次拉齐昵称（实现：`InternalUserController`，手机号脱敏） |
| `UserApi.listFriends` | 复用既有契约 | 好友榜过滤数据源（一次拉取，不逐条远程调用） |

### 3.4 事件与 Redis 键速查

| 键/事件 | 类型 | 用途 |
| --- | --- | --- |
| `record-verify-events`（Tag VERIFIED/REJECTED） | RocketMQ | 判定/终判事件源（verify 发布，本变更新增消费组 `leaderboard-consumer-group`） |
| `leaderboard:event:{eventId}` | Redis SETNX | 消费幂等（24h TTL） |
| `leaderboard:overall` | Redis ZSet | 热读层（member=userId，score=累计 pass 里程） |
| `lock:rollback:{recordId}` | Redisson 锁 | 入榜/回滚互斥（3s 等待，30s 看门狗） |
| `lock:scheduler:leaderboard` | Redisson 锁 | 定时结算防重（lease=-1 → 默认 30s 看门狗自动续期） |
| `record-verify-events-dlq` | RocketMQ DLQ | 消费重试超 3 次投递，人工排查 |

## 4. 三个核心设计（面试弹药：为什么不会出问题）

### 4.1 双层结构：ZSet 热读 + 锚点表权威（最终一致）

- **读多写少**：榜单查询全走 ZSet（`ZREVRANGE` 秒级），不碰 DB；
- **写权威在表**：`leaderboard_contribution`（record_id 主键）是回滚锚点与对账权威源——
  回滚按锚点行的 `distance/user_id` 精确扣回，不信任事件体重放值；
- **对账自愈**：结算任务每 10min 以锚点表 SUM 汇总覆盖 ZSet 并清理残留成员——
  Redis 键整体丢失也能从表重建（ZSet 只是加速层，漂移必收敛）。

### 4.2 三层幂等：SETNX → 锚点状态机 → 主键

1. **消费幂等**：eventId SETNX（24h TTL），重复投递直接跳过；
2. **业务幂等**：入榜先 INSERT IGNORE 锚点——命中 1 行（新贡献）才加分；命中 0 行看锚点状态
   （ROLLED_BACK → 重激活补加分，覆盖「驳回后再改判通过」；ACTIVE → 重复事件跳过）；
   回滚走乐观 UPDATE（ACTIVE→ROLLED_BACK）——影响 0 行 = 已回滚或无贡献，不扣分；
3. **物理幂等**：record_id 主键从库层面保证一条记录至多一行贡献。

去重键过期/重放、MQ 重复投递、消费重试——任意一层失效都由下一层兜住。

### 4.3 并发安全与防重：两把锁各管一事

- **`lock:rollback:{recordId}`**：同一记录的入榜与回滚互斥（规范「回滚与入榜并发安全」）。
  与点赞域「SADD 原子判重无需锁」不同——入榜/回滚是「查锚点→改状态→改 ZSet」多步操作，
  必须串行化才能保证锚点状态与 ZSet 一致；拿不到锁抛异常交 MQ 重投（不跳过，入榜不可丢）；
- **`lock:scheduler:leaderboard`**：结算任务多实例防重（lease=-1 走 30s 看门狗自动续期，
  与点赞 flush/好友互加同款，审批版 §7.5）。

已知权衡（诚实口径）：结算的「汇总 SELECT → ZADD 覆盖」期间并发的入榜增量会被下一轮结算收敛，
结算期间并发的回滚同理——这正是「最终一致」的定义，热读层实时由事件维护，对账只兜漂移。

## 7. 如何自己验证（起栈后四步）

前置：`docker compose up -d` 起中间件（首次会自动执行 sql/ 建表脚本），`mvn clean install` 后启动四个服务。
造数：跑一条真实链路（提交记录 → MQ 触发校验 → PASSED 判定回调 + VERIFIED 事件），或直接插库模拟：

```sql
-- 模拟一条已通过记录（真实链路则由校验引擎判定产生）
INSERT INTO record_db.sport_record (request_id, user_id, sport_type, distance, status, version, created_at)
VALUES ('lb-demo-001', 100, 1, 42.50, 2, 1, NOW());
-- 模拟 VERIFIED 事件已消费（或直接手动向 record-verify-events 发 Tag=VERIFIED 消息）
INSERT INTO record_db.leaderboard_contribution (record_id, user_id, distance, status)
VALUES (<上一步得到的记录id>, 100, 42.50, 0);
```

```bash
# 1. 总榜（ZSet 有数据后；也可等结算任务自动从锚点表重建 ZSet，首跑延迟 1min）
curl 'http://localhost:8080/record/api/leaderboard?type=overall&size=10'
# → data: [{ "rank": 1, "userId": 100, "nickname": "...", "distance": 42.5 }]

# 2. 好友榜（先给 100 与查询人建好友关系，再查）
curl 'http://localhost:8080/record/api/leaderboard?type=friend&userId=200'
# → 只显示好友 100；非好友用户即使里程更高也不出现

# 3. 回滚验证：把锚点行改回 ROLLED_BACK 前的状态重放 REJECTED 事件（或手动触发）
#    榜单分数应减去 42.5；重复回滚不再扣（幂等）

# 4. 结算核对（等 @Scheduled 首跑，或观察日志「榜单结算完成」）
SELECT record_id, user_id, distance, status, settled_at FROM record_db.leaderboard_contribution;
# → ACTIVE 行已盖 settled_at；ZSet 分数 = 各用户 ACTIVE 贡献 SUM
```
