# 变更提案：verify-service 端到端全链路容量与压测重评（measure-verify-e2e-capacity）

## 1. Why

在既有演进中，针对判定链路与事件投递基础设施的多项关键优化已陆续落地并经单元测试与局部基准验证：
1. **TASK-163**：`verify.outbox.relay-interval-ms` 默认调度间隔由 5000ms 缩减至 500ms（排空斜率提升 4.05×）；
2. **TASK-169**：`verify.outbox.relay-batch-mark-enabled` 开启分块批量标记（chunk-size 25），单行标记耗时降低 75%~91%，锁内吞吐稳定提升 4.87×；
3. **TASK-171**：`verify.outbox.relay-send-concurrency` 开启批内并发投递（N=2），并行化网络 RPC，锁内吞吐进一步提升 ≥1.5×；
4. **TASK-173**：落地 `RecordWithPointsDTO` 与 `RecordApi.getRecordWithPoints` 判定预取聚合契约，跨服务 Feign 往返由 2 次收敛为 1 次，主表查询由 2 次收敛为 1 次。

**测量动因与既有空白**：
- 上述四项优化均为局部代码改动、隔离 IT 或局部微基准度量，**从未在同一运行轮次下进行端到端全链路容量复评**；
- 历史端到端分段归因基准（**TASK-143**）仅为四服务局部覆盖（gateway/user/record/verify），且当时 R5 空间离路判定因 mapmatch/PostGIS 缺席而处于全降级状态（Resilience4j 3s 读超时兜底），leaderboard-service 亦缺席未启动；
- 早期压测基准（**TASK-138** / 审批版压测报告）对应旧 HEAD、旧参数与旧服务栈，不能代表当前 HEAD 的容量与延迟特征。

因此，本提案立项在真实全量中间件环境中执行端到端全链路压测，重新测定判定服务系统的饱和吞吐量与 P99 延迟水位，形成客观基准。

---

## 2. What Changes

### 2.1 变更性质：纯测量类提案
- **零生产变更**：`src/` 生产代码、应用配置文件、默认参数、SQL DDL/DML、pom.xml、`scripts/` 脚本零修改；
- **产出物范围**：限定为 `docs/perf/` 下的压测报告与机器摘要 JSON、本提案三件套、任务书及收口验收台账。

### 2.2 测量目标与链路覆盖面
- **覆盖目标**：端到端全链路覆盖——包含 gateway-service、user-service、record-service、verify-service、leaderboard-service、mapmatch-service 六个业务服务，以及 MySQL、Redis、RocketMQ、PostGIS 四大基础设施，R5 空间真实性校验不降级；
- **环境降级分支预注册**：
  - 若真实环境中 mapmatch/PostGIS 容器或路网数据无法就绪，或 leaderboard-service 无法拉起，必须如实按「局部覆盖（列明缺席项）」降级登记，严禁伪称全链路，严禁为凑齐覆盖而修改生产配置或代码；
  - 若连基础四服务（gateway/user/record/verify）与核心中间件均无法安全就绪，必须如实登记「测量未执行」并以证据不足支收口，严禁伪造或推导实时吞吐读数。

### 2.3 指标口径与测量矩阵
1. **客户端提交指标**：c100×2000（100 并发 × 2000 请求，含 10 预热）负载下的有效 QPS、墙钟耗时、P50 / P95 / P99 延迟、成功率与限流错误率；
2. **事件分段耗时（复用 TASK-143 口径）**：
   - `pub→consume`：record 发布到 verify 消费开始（跨进程队列积压）；
   - `consume→callback`：verify 消费开始到判定落库与回调完成（计算+数据操作）；
   - `callback→SENT`：判定完成到 outbox relay 标记 SENT（排队投递）；
   - 端到端 `consume→SENT` 与 `pub→SENT`；
3. **判定完成速率**：单位时间完成终态判定的记录数（records/s）；
4. **outbox 排空斜率（复用 TASK-163 口径）**：负载停止后由 relay 驱动的 PENDING 排空速率（rows/s）；
5. **积压盘点分账**：区分可投递 PENDING（`retry_count < maxRetry`）与待人工 PENDING（`retry_count >= maxRetry`）。

### 2.4 预注册实验纪律
- **对照与轮次框架**：继承 TASK-156/161-164 预注册框架，包含丢弃的预热轮（W0）与正式计数轮；
- **抗 QPS 单调漂移对策**：汲取 TASK-144 与 TASK-162 中提交 QPS 随宿主预热单调上漂导致可比性门（±15%）失效的教训，优先采用与提交 QPS 解耦的指标（如负载停止后的排空斜率、同进程锁内耗时、消费排空耗时）作为核心判定依据；
- **历史数据纪律**：TASK-138 与 TASK-143 读数仅登记为历史背景参考，不做翻案裁决、不计算改善百分比、不为生产真实容量背书。

---

## 3. Impact

- **规范与代码**：主规范与各模块代码零修改，系统运行时行为零漂移；
- **测试预算**：单元测试保持 450 用例全绿，不新增单元测试；若后续需保防护件只能 test-only 且默认关闭；
- **数据与安全**：压测产生的数据保留在演示库，严禁 TRUNCATE / 清库 / 破坏既有数据卷；
- **外部效力**：所有实测性能指标严格限定于「本机环境、本负载模型、未达外部门槛」，不作外推背书。

---

## 4. 判定与停止条件

1. 若实施测量需要修改任何生产代码、SQL、服务默认配置或 pom 依赖 ⇒ **停止**，并登记为候选后续优化提案；
2. 若在测量准备或执行过程中发现任何顺手优化的冲动 ⇒ **严格禁止并停止**；
3. 若测量过程中发现判定状态机异常、事件丢失、数据破坏等语义错误 ⇒ **立即停止并留证回报**；
4. 若真实环境无法支持全链路且无法安全执行降级局部测量 ⇒ **停止**，按「环境不足未执行」收口；
5. 若磁盘容量不足、数据库或消息队列异常退出且无法自愈 ⇒ **停止**。
