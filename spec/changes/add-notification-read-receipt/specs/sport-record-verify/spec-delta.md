# spec-delta：通知已读回执（TASK-186 add-notification-read-receipt）

## ADDED 需求：通知已读回执（跨端已读同步）

### 场景

1. 用户在 A 端单条标记已读成功 → 该用户全部在线会话（含 A 端）在秒级收到已读回执 → 铃铛未读数刷新、已打开的通知列表重载，B 端不再显示已读项为未读。
2. 用户在 A 端全部已读成功（影响行数 N>0）→ 全部在线会话收到**一条** kind=all 回执（不逐条发）→ 同场景 1 反应。
3. 通知不存在 / 非本人归属 / 已是已读态（影响行数 0）→ **不发回执**（幂等重复标记不产生事件）。
4. 回执发布或投递失败 → 仅服务端告警，REST 已读操作返回值不受影响；跨端同步退化为 60s 轮询兜底（不劣于 TASK-183 基线）。
5. 收件人无任何在线会话 → 回执按 Spring「无会话用户不投递」语义静默丢弃（回执不持久化、不补偿）。
6. 未登录前端不建立 WS 连接、不订阅任何队列（既有红线 §0.2 语义延伸到第二队列）。
7. 前端收到回执与收到新推**反应同构**：刷新未读数 + 重载已打开的通知列表（复用同一回调，属预注册设计决策，不是缺陷）。
8. WS 断流期间发生的已读操作 → 重连后不补发历史回执（回执是瞬时事件）；跨端一致性由轮询兜底自愈。
9. REST 已读接口契约（路径/参数/返回语义）零改动——回执是服务层内部事件，不新增任何 REST 端点。

### 验收断言

- 单测（offline 确定性）：markRead 成功 → 恰一条 kind=single 回执（含 notificationId 与 readAt）；markRead 零行 → 零回执；markAllRead N>0 → 恰一条 kind=all 回执；markAllRead 零行 → 零回执；publish 异常 → 返回值不变；relay 收到回执 JSON → convertAndSendToUser 正确用户与 `/queue/notification-read` 目标；非法载荷丢弃告警。
- 前端：第二队列订阅存在且回调复用；未登录 no-op 语义不变；type-check / build / typed-router 零漂移 / frozen-lockfile 全绿。
